## 1. 背景与问题

当前行为级审核已经能把每条提交快照独立裁决为 `pending | approved | rejected`（见[行为级审核 API 契约](../behavior-review-api.md)），但视频级终局与片段发布仍绑死在一起：

- 视频级 `POST /review` 只在 `result=approved` 时创建片段与媒体任务，且一次性为全部提交快照创建 Clip。
- 片段库、类别计数、缩略图权限与新导出都要求 `Submission.status = approved`，导致任何一次 `rejected` 尝试里已经逐条通过的行为无法作为训练资产使用。
- 一旦 reopen / superseded / 后续提交 / track 修复 / 检测基线替换，旧资产会因查询过滤而"看起来下架"，即使实体与不可变快照仍然存在。

本计划把"视频级发布审核结果"与"逐条行为的永久片段发布"解耦：视频级结果只决定这次审核结论，逐条通过的行为各自形成永久发布资产。

## 2. 目标与非目标

### 2.1 目标

1. 视频级操作改称"发布审核结果"，并明确其门禁。
2. 发布事务内仅为**当时逐条通过的子集**创建永久发布资产（submission-bound Clip）与媒体任务。
3. 已发布资产不因 reopen / superseded / 后续提交 / track 修复 / 检测基线替换自动下架或重生成。
4. 片段库、类别计数、缩略图权限与新导出改为以"已发布资产事实"为准，不再按 `Submission.status` 过滤。
5. 常规 carry 采用 canonical asset reuse，不重复创建/转码导出内容完全相同的资产。
6. 全程零 schema 变更。
7. 明确 legacy 兼容与未来回填边界。

### 2.2 非目标

- 不新增表、列、索引或 trigger，不新增持久内容哈希字段。
- 不把结构化发布数据写入 `Review.comment`（`comment` 只保留人类可读审核意见）。
- 不实现 legacy 快照的 submission-bound Clip 回填（见第 5.8 节 TODO）。
- 不改变逐条裁决、退回重提、reopen 与误退判定的既有语义。
- 不把视频硬删除之外的任何动作定义为资产删除边界。

## 3. 设计结论：零 schema

复用现有四类不可变/追加记录，不新增任何数据库结构。本发布特性不新增迁移，既有 Alembic head 保持 `0018`（`0018_feedback_marks`），不创建 `0019`；`backend/app/models.py` 与 `backend/migrations/` 对本特性不改。

| 复用对象 | 在发布模型中的角色 |
|---|---|
| `Review` | 视频级**发布审核结果**（`approved` / `rejected`）的唯一终局记录，一行一次视频级终局。 |
| `BehaviorReviewDecision` | 逐条裁决的只追加审计，最大 `sequence` 为当前裁决；是"approved 子集"的唯一来源。 |
| `SubmissionAnnotation` + `DetectionSnapshot` | 不可变被审数据与检测/姿态权威，导出内容只从这里读取。 |
| `Clip`（`submission_annotation_id` 绑定） | 逐条**永久发布资产**；行存在即"已发布训练资产事实"，`Clip.status` 仅表示生成进度。 |

明确否决：把 approved 子集、资产标识或导出元数据塞进 `Review.comment` 或其他文本列。该方案会引入不可查询、不可约束的隐式结构，且与"零 schema"目标相比更脆弱。

## 4. 术语

| 术语 | 定义 |
|---|---|
| 发布审核结果 | 现有视频级 `POST /review` 的产品语义重命名；产出 `approved` 或 `rejected` 终局 `Review`。 |
| approved 子集 | 发布事务那一刻，该提交中最新逐条裁决为 `approved` 的 `SubmissionAnnotation` 集合（含 `origin=carried`）。 |
| 已发布资产 | 绑定到某个 `SubmissionAnnotation` 的 `Clip` 行；行存在即已发布，`status` 只表示生成进度。 |
| canonical 已发布资产 | approved 子集某项解析到的、导出内容完全相同的已发布 `Clip`；相同 carried 复用该资产而不新建行。 |
| 资产内容 | 该资产导出包（`clip.mp4` / `annotation.json` / `tracks.json` / `metadata.json`）的全部不可变输入。 |
| legacy 兼容路径 | 片段库/缩略图中基于实时 `Annotation` + `review_status=approved` 的旧查询分支。 |

## 5. 产品与门禁

### 5.1 视频级发布门禁

| 结果 | 门禁 |
|---|---|
| `approved` | 仅当该提交**全部**快照的最新裁决均为 `approved`（carried 计入）才允许；否则 409 `behavior_decisions_incomplete`。 |
| `rejected` | 必须至少有**一条**快照的最新裁决为 `rejected`；`pending` 可与 `rejected` 共存。 |
| 禁止 | 不允许用 `rejected` 绕过"无退回时全部通过"：若不存在任何最新 `rejected` 裁决（例如全部 `pending`/`approved`），视频级 `rejected` 必须 409，而不是把 `pending` 当作未通过。 |

- 现有 `expected_submission_id` / `expected_decision_revision` 并发上下文保持不变，两种结果共用同一门禁。
- 视频级退回**不**伪造逐条拒绝；`pending` 条目保持 `pending`。
- **与线上现状的差异**：现行 [行为级审核 API 契约](../behavior-review-api.md) 只要求 `rejected` 允许保留 `pending`，并未要求至少一条 `rejected`。"至少一条最新 `rejected`"门禁已在本分支实现（见第 10 节），但尚未部署；权威正文在部署并验证前继续描述线上实现，届时再同步。

### 5.2 发布事务

同一短事务、同一 commit 内完成：

1. 以 CAS 将 `Submission.status` 从 `submitted` 改为终局（`approved` / `rejected`）。
2. 写唯一 `Review`（含 `result`、人类可读 `comment`）与 `Submission.decided_at`；`approved` 时按现有规则把同视频旧 `approved` 置 `superseded`。
3. 对**当时 approved 子集**的每一项做 canonical asset reuse：解析到已存在且导出内容完全相同的已发布 `Clip`（canonical 资产）则直接复用，否则为当前快照新建 submission-bound `Clip(status=pending)`。carried 快照若命中相同历史资产则**不**新建 `Clip`，其资产仍从历史 Clip 可达；`pending` / `rejected` 快照**不**创建任何 `Clip`。
4. 仅当第 3 步确实新建了 `Clip` 或存在需要重试的 `Clip` 时，才为这些快照写媒体 `BackgroundJob`（payload 只含本次新建或需重试的 `submission_annotation_id`）；空集合**不**创建 job。
5. **commit 之后**才调度 worker；调度失败不回滚终局，靠持久 `queued` 任务恢复。

说明：`approved` 终局因门禁要求全部通过，其 approved 子集等于全部快照；`rejected` 终局只发布其中逐条通过的行为。由于 canonical reuse，已发布资产数可以少于 approved 子集项数（相同 carried 不重复建资产）。

### 5.3 资产事实与 `Clip.status`

- `Clip` 行存在 = 已发布训练资产事实；submission-bound DB 行的 `Clip.status ∈ {pending, processing, ready, failed}` 只表示生成进度，不表示是否已发布。`stale` 只是 legacy 读取路径的派生显示值（旧 `Annotation` + 修订不匹配时在查询层计算），**不**作为新资产行的生命周期状态写入数据库。
- 片段库、类别计数、缩略图权限、新导出**不再**按 `Submission.status` 过滤；`rejected` 提交的 approved 子集资产可正常浏览、取缩略图与导出。
- `ready` 但仍缺少实体文件时按现有 `_resolve_entity` 规则降级为不可用（沿用当前 `media_status=pending` 行为），不得因为生成失败而删除已发布行。

### 5.4 资产永久性

已发布资产不因以下事件自动下架、删除或重生成：

- `reopen` / `superseded`；
- 后续提交或后续审核结果；
- track 修复（Split/Merge/Suppress/Undo）或检测基线替换；
- 视频投影回退为 `draft/rejected`。

导出包内 `annotation.json` 与 `tracks.json` 必须来自同一不可变 `DetectionSnapshot`，不得在导出时重读当前 draft。片段内 ID 只要求能在片段内部指明行为鼠；**不保证**跨片段一致，也**不保证**与网站当前显示 ID 一致。

视频硬删除仍是显式删除资产的唯一边界；除硬删除外没有隐式下架。

### 5.5 常规 carry 与 canonical asset reuse

- `pending` 在下一轮提交继续为 `pending`；已通过行为按现有规则以 `origin=carried` 携带通过。
- **canonical asset reuse**：发布时，approved 子集的每一项（显式通过或 carried）要么解析到一个已存在且导出内容完全相同的已发布 `Clip`，要么为当前快照新建一个 `Clip`；approved 子集每项恰好解析到一个 canonical 已发布资产，相同 carried 不新建 `Clip`、不重复转码。
- 当前 carried 快照本身没有绑定 `Clip` 是有意设计：资产事实仍从它解析到的历史 `Clip`（经 `Clip.submission_annotation_id` → 历史 `SubmissionAnnotation`）可达，不要求为每个 carried 快照各留一行资产。
- 片段库、导出与统计查询必须从 submission-bound `Clip` **inner join** `SubmissionAnnotation`/`Submission` 起步，不能从最新 `SubmissionAnnotation` outer join `Clip` 起步；否则会把无 Clip 的 carried 快照错误地当成缺失资产。
- 若解析不到等价资产，或新快照会改变导出包内容，则为当前快照新建资产并保留旧资产。判定"内容完全相同"的既有不可变字段：
  - 身份与去重键：`SubmissionAnnotation.source_annotation_key`、`source_material_revision`、`material_digest`；
  - 源视频身份：`Submission.source_storage_key`、`source_video_sha256`、`source_file_size`、`source_mtime_ns`、`source_device`、`source_inode`；
  - 帧区间与裁剪：`SubmissionAnnotation.start_frame` / `end_frame` / `crop_region`；
  - 行为字段与参与 ID：`category_name`、`category_participant_mode`、`role_definitions_snapshot`、`participant_roles_snapshot`、`mouse_ids`、`confidence`；
  - 检测权威：`DetectionSnapshot.raw_digest` / `state_digest` / `metadata_digest`；
  - 导出 schema/profile：`metadata.json` 的 `schema_version` 与导出契约版本。
- 任一导出内容输入变化即创建新资产并保留旧资产；**不引入**持久内容哈希列，比较只在查询侧用上述现有不可变字段完成。

### 5.6 误退不新增机制

沿用现有规则，不引入新表或新状态：

- 被退回行为需**实质修改或删除**才能重提；
- 或审核人显式把该条裁决改回 `pending`；
- 改其他行为、或把值改回原值（`reverted`），均不解除 blocker。

### 5.7 `FeedbackMark.marked` 与材料差异的边界

`0018_feedback_marks` 的 `FeedbackMark`（`marked`）是**标注页人工处理标记**：审核人/标注人把某条退回意见标为“已修改”的 UI 状态与审计记录，便于跟进处理。它**不**参与 `rejected_blockers` 的 blocker 判定、视频级发布门禁，也不决定片段资产可用性与导出资格。

判定“退回是否被实质修改”的唯一依据仍是 `decision_comparison`：只有 `modified`（或原标注已删除的 `deleted`）构成材料差异，`unchanged` 与 `reverted` 仍为 blocker。`marked` 与 `comparison=modified` 相互独立，不得互相推断。

因此后续改 `backend/app/routers/reviews.py`、`backend/app/behavior_review.py`、`backend/app/video_delete_db.py` 时必须保留：

- `FeedbackMark` 的读/写接线（`behavior_review.py` 的 `feedback_marks` / `record_feedback_mark`，`reviews.py` 中 `marked` / `marked_at` 的序列化与排序）；
- `video_delete_db.py` 的 `_ID_MODELS`、`_DELETE_ORDER` 与 `feedback_marks` 收集逻辑，删除顺序保持 `feedback_marks` 早于 `submission_annotations`。

### 5.8 legacy 兼容与回填 TODO

- legacy 数据当前仍走查询兼容路径（片段库/缩略图的实时 `Annotation` 分支），在回填完成前**不得移除**。
- **逐行为/逐资产 anti-join**：不能再用"该视频存在任意 `Submission` 就整视频排除 legacy"的 `authority_video_ids` 方式。只有同一 `video_id` + `source_annotation_key` 已经存在 submission-bound `Clip` 时，才排除对应的 legacy 行；否则保留。这样部分发布（同一视频只有部分行为发布）不会让同视频其他 legacy 资产凭空消失。

## 7. 最小验收不变量

1. **门禁**：`approved` 仅在全部最新裁决 `approved` 时成功；`rejected` 至少一条最新 `rejected`；无任何 `rejected` 时 `rejected` 返回 409 且零状态变化。
2. **发布原子性**：发布 commit 后，approved 子集每项恰好解析到一个 canonical 已发布资产；相同 carried 不新建 `Clip`，`pending`/`rejected` 快照无 `Clip`；媒体任务 payload 只含本次新建或需重试的 snapshot ID，空集合不建 job；调度失败时终局已提交、任务保持 `queued`。
3. **资产事实**：submission-bound `Clip` 行存在即可被片段库/类别计数/缩略图/导出看到，且与 `Clip.status` 无关；`rejected` 提交的 approved 子集可导出；查询从 Clip inner join SubmissionAnnotation/Submission 起步，carried 快照无自身 Clip 也不被当成缺失。
4. **永久性**：`reopen`/`superseded`/后续提交/track 修复/检测基线替换后，旧 `Clip` 行、`clip_path`、`status` 与实体不变，不触发重生成。
5. **导出同源**：`annotation.json` 与 `tracks.json` 来自同一 `DetectionSnapshot`；片段内 ID 自洽即可，不断言跨片段或与当前网站 ID 一致。
6. **carry 去重（canonical reuse）**：导出内容完全相同的 carry 解析到既有资产、不新建 `Clip`/任务；任一既有不可变字段（含 `source_annotation_key`、`source_material_revision`、`material_digest`）变化则新建资产且旧资产保留；过程中不写任何内容哈希列。
7. **误退**：改其他行为或改回原值不解除 blocker；实质修改/删除或改回 `pending` 才解除。
8. **legacy**：兼容查询分支仍生效，且按 `video_id` + `source_annotation_key` 逐行 anti-join，部分发布不隐藏同视频其他 legacy 资产；未实现回填前不得删除。
9. **零 schema**：本发布特性不新增迁移，既有 Alembic head 保持 `0018`（`0018_feedback_marks`），不创建 `0019`；`models.py` 与 `backend/migrations/` 对本特性不改；`PRAGMA foreign_key_check` 与 authority trigger 不变。

## 10. 已实现范围

本分支 `feature/per-behavior-release` 已实现（未提交 / 未部署 / 未做真实浏览器人工验收）：

- **发布门禁**：`approved` 仅当全部快照最新裁决通过；`rejected` 至少一条最新退回，无退回时 409 `no_rejected_behavior` 且零状态变化；`pending` 可与 `rejected` 共存；CAS 与既有 409 code 保留。
- **单一发布动作**：前端视频级唯一「发布审核结果」动作；存在未处理行为时以阻断弹窗提示且不提交。
- **发布事务 canonical asset reuse**：仅复用已就绪（`ready` 且实体文件存在）或在途（`pending`/`processing` 且有未完成 job）的等价资产；`failed` 或实体缺失的等价资产通过重排既有 `Clip` 所属提交的 job 补生成，不新建重复 `Clip`、不产生重复 `ready` 资产、不重编码已就绪资产；`pending`/`rejected` 不建 Clip；空集合不建 job；commit 后调度。
- **媒体**：worker（`_process_submission_job`）与 `media-status`/`media/generate` 放行终局 `rejected` 中已发布的 approved 子集；`_upsert_submission_job` 在 `queued` 时把新的 snapshot id 合并进既有 payload（去重、稳定排序），`running` 不改写。
- **读取路径**：片段库/类别计数/缩略图/导出改为从 submission-bound `Clip` inner join `SubmissionAnnotation`/`Submission` 起步，去掉 `Submission.status == approved` 过滤；legacy 分支保留并按 `video_id` + `source_annotation_key` 逐行 anti-join。
- **零 schema**：未改 `models.py`/`migrations/`，Alembic head 保持 `0018`，不创建 `0019`。
