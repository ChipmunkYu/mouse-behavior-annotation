# 分工标注模块需求文档

> 状态：需求已确认，尚未实现
> 日期：2026-08-10
> 对应工作项：WI-20260810-24
> 关联文档：[需求文档](../../需求文档.md)

## 1. 模块定位

分工标注模块用于在项目内明确每个视频的当前负责人，并提供领取、改派、查找和数量统计能力。首版只按完整视频分工，不分配时间段，不新增独立任务状态机或 `Task` 表。

分工只表示责任归属，不构成编辑权限隔离。所有项目成员仍可编辑项目视频；行为标注继续记录真实 `Annotation.annotator_id`，track 修正仍是视频级共享结果。

本文描述计划新增能力。当前实现仍采用 `owner/admin/annotator/reviewer` 项目角色，尚无本文所述负责人、领取、成员审核开关和单一邀请码完整能力。

## 2. 用户场景

以下为计划交互流程，当前代码尚未实现。

1. owner/admin 导入视频时可选当前负责人，也可保持未分配。
2. owner/admin 在视频库批量分配或改派视频，并按负责人查看工作量。
3. 任一项目成员从“待领取”视图领取未分配视频；并发领取时仅首个请求成功。
4. 当前负责人从“我的任务”进入视频并完成标注；其他成员仍可进入和编辑，所有操作保留真实操作者。
5. 当前负责人可在视频仍为 `draft` 时释放；视频回到未分配状态，已有标注和 track 修正不删除。
6. 标注完成后沿用视频级提交审核；审核通过或退回后仍保留当前负责人，退回继续由原负责人处理。

## 3. 成员管理

### 3.1 当前实现与计划模型

| 范围 | 当前实现 | 分工模块计划 |
|---|---|---|
| 项目角色 | `owner/admin/annotator/reviewer` | 简化为 `owner/admin/member` |
| 审核能力 | 主要由角色区分 | owner/admin 默认具备；member 由 `ProjectMembership.can_review` 单独授权 |
| 普通成员 | `annotator`、`reviewer` 分立 | 统一为 `member`，审核能力与成员身份解耦 |

上述目标模型须通过后续数据迁移和权限改造实现，不得把计划角色体系当作当前代码事实。现有成员数据的具体迁移映射在实现设计阶段确认；本需求不定义 reviewer 角色转换规则。

### 3.2 管理规则

- owner/admin 均可查看成员、管理成员身份，并为 member 授予或取消 `can_review`。
- 项目 owner 不能被移除或降级。
- 成员仍是任一视频的当前负责人时，禁止移除；owner/admin 须先改派或释放相关视频。
- 所有 owner/admin/member 均可领取未分配视频。
- 具备审核能力的成员可以审核自己负责或参与标注的视频，不禁止自审。

### 3.3 邀请码

- 每个项目使用一个邀请码。
- owner/admin 可生成、查看和重置邀请码。
- 邀请码长期有效，直到被重置；重置后旧邀请码立即失效。
- 用户输入有效邀请码后以 `member` 身份加入项目。

## 4. 分配模型

- 分配单位固定为完整视频。
- 一个视频最多有一个当前负责人，也可以未分配。
- 当前负责人保存于 `Video`，不新增 `Task` 表。
- 首版不保存分配、改派、领取或释放历史。
- 负责人变化不修改既有 Annotation；`Annotation.annotator_id` 始终保留真实原作者。
- 负责人变化不修改或清空共享的 track 修正结果。
- 上线时所有存量视频均保持未分配，不根据上传者、历史标注作者或其他字段推断负责人。

## 5. 分工流程

### 5.1 分配与领取

- 视频导入成功时，owner/admin 可指定当前负责人；未指定时进入“待领取”。
- owner/admin 可在视频库对一个或多个视频批量分配或改派。
- 任一项目成员可领取未分配视频。服务端必须在单个事务内检查未分配并写入当前负责人，实现原子“先到先得”；竞争失败返回冲突结果并刷新列表。

### 5.2 释放与改派

- 仅当前负责人可主动释放自己的视频，且视频必须仍为 `draft`。
- 释放后只清空当前负责人；已有 Annotation、审核相关数据和 track 修正均保留。
- owner/admin 首版仅可在 `draft` 或 `rejected` 阶段改派或清空负责人；`submitted`、`approved` 阶段禁止改派。
- 改派后新负责人接手后续处理，已有标注的 `annotator_id` 不改写。

### 5.3 标注与审核

- 分工不改变项目成员既有的视频编辑权限，非负责人仍可标注和执行视频级 track 修正。
- 任务完成直接使用现有视频级提交审核，不新增“任务完成”操作或任务状态。
- 提交、通过、退回均保留当前负责人；`rejected` 视频由原负责人继续处理，除非 owner/admin 改派。
- 具备审核能力的成员可审核自己负责或参与标注的视频。

## 6. 进度统计

首版仅统计任务数量，不计算标注时长、事件数、类别完成率或个人编辑贡献。

| 统计项 | 计算口径 |
|---|---|
| 负责视频数 | 当前负责人为该成员的视频总数 |
| 待处理 | 当前负责人为该成员且 `workflow_status=draft` |
| 待审核 | 当前负责人为该成员且 `workflow_status=submitted` |
| 通过 | 当前负责人为该成员且 `workflow_status=approved` |
| 退回 | 当前负责人为该成员且 `workflow_status=rejected` |
| 未分配数 | 当前负责人为空的视频总数 |

统计直接依据 `Video.workflow_status` 和当前负责人计算，不落独立任务状态。owner/admin 可查看全部成员统计；普通 member 至少可查看自己的统计及项目未分配数。

## 7. 页面架构

### 7.1 视频库

- 提供“我的任务 / 待领取 / 全部”三个视图。
- “我的任务”仅显示当前用户负责的视频；“待领取”仅显示未分配视频；“全部”显示项目全部视频。
- 卡片或列表显示当前负责人和 `workflow_status`；待领取项提供领取操作。
- owner/admin 可按负责人筛选，在“全部”视图批量分配、改派或清空负责人。

### 7.2 导入流程

- 计划扩展现有 API/UI：单视频上传确认时，以及三文件导入批次完成时，均提供可选负责人选择器。
- 不选择负责人不阻断导入；成功后视频进入待领取视图。

### 7.3 项目管理

- 成员管理展示计划角色、审核能力开关和负责视频数。
- owner/admin 可管理成员、邀请码和 member 的审核能力。
- 移除仍负责视频的成员时，界面提示须先处理其负责视频，不提供静默清空。
- 进度区按成员展示第 6 节规定的数量统计，并单独展示未分配数。

## 8. API 需求

以下仅定义需求级操作，具体路径可在实现设计时与现有路由统一。

| 操作 | 权限与要求 |
|---|---|
| 查询视频列表 | 支持 `mine/unassigned/all` 视图、`workflow_status` 和负责人筛选 |
| 导入视频时指定负责人 | owner/admin；负责人必须是当前有效项目成员，可为空 |
| 批量分配、改派或清空负责人 | owner/admin；校验项目归属及 `draft/rejected` 状态，操作应整体返回逐项结果 |
| 领取未分配视频 | 任一项目成员；原子条件更新，已被领取时返回 409 |
| 当前负责人主动释放 | 当前负责人；仅允许 `draft`，否则返回 409 |
| 查询分工统计 | 返回各成员负责总数及四种 `workflow_status` 数量、未分配数 |
| 查询和管理成员 | owner/admin 可变更计划角色、member 的 `can_review` 或移除成员；应用 owner 和负责视频约束 |
| 生成、查看、重置邀请码 | owner/admin |
| 通过邀请码加入项目 | 已登录用户；有效邀请码使其以 member 身份加入，重复加入按现有成员唯一约束处理 |

所有写操作必须校验当前用户的项目成员身份、目标成员与视频的项目归属，不能仅依赖前端隐藏入口。

## 9. 数据模型变更

### 9.1 ProjectMembership

- 计划将 `role` 约束调整为 `owner/admin/member`。
- 新增成员级 `can_review` 布尔字段；owner/admin 的审核能力由角色保证，member 读取该字段。
- 保持 `project_id + user_id` 唯一。
- 角色迁移属于计划变更，需在实现阶段提供数据库迁移和现有数据校验。

### 9.2 Video

- 新增可空的当前负责人外键，建议指向 `ProjectMembership`，保证负责人属于同一项目。
- 为项目、当前负责人、`workflow_status` 的列表筛选和统计建立必要索引。
- 存量记录迁移后当前负责人统一为 `NULL`。

### 9.3 明确不新增

- 不新增 `Task` 表或任务状态字段。
- 不新增分配、改派、领取、释放历史表。
- 不为 Annotation 增加“负责人”副本，不改写 `annotator_id`。

## 10. 非功能约束

- **并发一致性**：领取必须使用数据库条件更新或等效事务机制，确保同一视频不会被两人同时领取。
- **权限安全**：服务端统一执行角色、审核能力、项目归属和工作流状态校验。
- **数据保留**：分配、释放和改派不得删除标注、审核数据、Clip 或 track 修正。
- **性能**：视频视图、负责人筛选和数量统计应使用数据库聚合，满足现有 3–5 人协作规模。
- **兼容上线**：迁移失败必须回滚；存量视频不得自动推断负责人。
