# 视频同步硬删除需求规格

> 状态：已实现并完成本地验证，尚未部署
> 日期：2026-08-22
> 基线：`main@285a554`
> 对应工作项：WI-20260805-22
> 约束：不新增数据库字段；生产安全前提为单 Uvicorn 应用进程 `--workers 1`；本文件只定义视频删除，不定义本轮标注流程重梳与时间/帧边界修复

## 1. 背景与问题

本功能针对基线版本的删除能力缺口；直接删除 `Video` 不能满足需求：

- `Submission.video_id`、`DetectionSnapshot.detection_import_id` 等不可变权威链使用 `RESTRICT`；
- `submission_annotations`、快照、快照状态和已被快照引用的原始检测受 SQLite trigger 保护，普通级联删除会被拒绝；
- 原视频、检测导入文件、片段、缩略图和导出 ZIP 分散在多个受控目录；
- 媒体任务和项目导出任务可处于 `queued/running`，其中一次项目导出可能同时包含目标视频与其他视频；
- `VideoImportBatch.created_video_id` 只会在视频删除后 `SET NULL`，若不主动处理会留下批次记录和重复文件引用；
- 数据库与文件系统之间没有共同事务，进程崩溃时可能出现“数据库已删、文件残留”或相反状态。

因此，本功能必须是一个受权限、状态、并发门禁和可恢复清理协议保护的业务操作，不能等同于 `db.delete(video)`。

## 2. 目标

1. 允许经确认的项目管理角色对单个视频执行**同步硬删除**。
2. 删除成功响应返回前，目标视频应从业务查询中消失，所有仅属于该视频的数据库记录与实体文件均完成清理。
3. 发现引用目标视频的 `queued` 或 `running` 媒体/导出任务时拒绝删除且保持零副作用；不存在活动关联任务时，清理非活动关联任务及其结果文件，并禁止删除后重新发布片段或 ZIP。
4. 不新增软删除标记、删除状态、墓碑或其他数据库字段。
5. 删除过程具有明确的失败结果、残留检测与恢复办法。
6. 不影响同项目其他视频、其他项目、类别方案、成员或无关任务。

## 3. 非目标

- 不提供回收站、撤销删除、延迟删除或批量删除。
- 不保留被删视频的标注、审核、提交快照或导出历史。
- 不删除项目、用户、类别方案或共享配置。
- 不处理项目外文件、越界路径或无法证明由系统持有的文件。
- 不在本功能中修改标注流程、时间输入方式或 inclusive end frame 转换；这些由后续独立规格补充。
- 不承诺数据库与文件系统具备真正的分布式原子事务；按第 11 节已确认的隔离清单恢复策略控制该边界。

## 4. 术语

| 术语 | 定义 |
|---|---|
| 同步硬删除 | 客户端发起删除后保持请求，直到删除成功或得到明确失败；成功后不保留业务可恢复记录。 |
| 目标视频 | URL 中 `project_id + video_id` 唯一定位且仍属于该项目的视频。 |
| 关联任务 | payload 或冻结权威引用直接或间接包含目标视频的媒体任务或项目导出任务。 |
| 独占删除门禁 | 删除期间阻止同一视频继续标注、提交、审核、检测替换、媒体生成或其他写入的并发控制。 |
| 实体文件 | 原视频、导入批次/检测文件、片段、缩略图、导出 ZIP 及本次任务临时产物。 |

## 5. 用户故事

### US-1 删除视频

有权限的用户在视频库看到删除入口，查看不可逆影响摘要，明确确认后删除视频。

### US-2 防止误删

无权限用户、非 active 成员、跨项目请求或不允许状态下的请求必须被拒绝，且不得改变数据库、任务或文件。

### US-3 处理运行任务

若目标视频存在 `queued` 或 `running` 关联任务，本次删除立即以 409 拒绝，不自动取消、不等待、不改变任务状态，也不移动或删除任何目标文件或业务数据；界面说明关联任务仍在排队或运行，并提示联系管理员解决。管理员处理完毕且不再存在活动关联任务后，用户可重试删除。

### US-4 失败可诊断

任一步骤失败时，调用者得到稳定错误；运维者可判断删除是否未发生、已发生但仍有待清理残留，或可安全重试。

## 6. 权限与可删除状态

已确认：

| 决策 | 结论 |
|---|---|
| 删除角色 | active `owner/admin` |
| 允许状态 | 仅 `draft/rejected`；`submitted/approved` 必须拒绝，不能以确认或 `force` 绕过 |
| 高风险状态确认 | 不适用，因为 `submitted/approved` 不允许删除 |

同时确认：owner/admin 不受负责人限制；`draft/rejected` 使用展示完整影响范围的普通危险确认，不要求输入文件名。

后端会重新验证 active membership、角色、项目归属和最新工作流状态；前端隐藏按钮不能替代授权。

## 7. 入口与 API 契约

### 7.1 后端端点

```http
DELETE /api/projects/{project_id}/videos/{video_id}
```

当前成功响应为 `204 No Content`。删除前检查失败不产生副作用。

当前错误语义：

| 状态码 | 场景 |
|---:|---|
| 403 | 非 active 成员或角色无权删除 |
| 404 | 项目内不存在该视频；重复删除也返回 404，不泄露跨项目资源 |
| 409 | 视频不是 `draft/rejected`、同视频有竞争写、存在 `queued/running` 关联任务、关联任务状态未知，或删除已由另一请求占用；活动任务场景须说明任务仍在排队或运行并提示联系管理员处理后重试，未知状态须按异常门禁提示联系管理员 |
| 500 | 删除过程发生内部错误；响应必须区分“未删除”与“数据库已删但残留待恢复” |

端点不需要确认文件名请求体或查询参数；不得使用 `force=true` 绕过权限、状态或路径安全检查。

### 7.2 前端入口

- 单视频卡片不提供删除按钮；active `owner/admin` 在“全部”视频视图选中视频后，通过统一选择操作栏执行删除。
- 操作栏将“改派”“删除可删除项”“取消选择”展示为三个同级操作组；改派组可因成员选择器占用更宽空间，但视觉层级保持一致。
- 多选删除仅处理所选视频中前端可判定为 `draft/rejected` 的项目，其余项目跳过并保留选择；所有权限、状态和并发安全判断仍以后端为准。
- 确认框汇总总选中数、可删除数和跳过数，明确逐个调用单视频 DELETE、操作永久不可恢复，且单项失败不会回滚已经成功的删除。
- 删除期间锁定改派、删除、取消选择、框选和筛选切换；成功项从列表与选择中移除，跳过项和失败项保留选择。
- 失败结果在统一操作栏附近汇总并提供可执行建议，不得把逐项执行描述为原子批量成功。
- 若因 `queued/running` 关联任务返回 409，明确提示“关联任务仍在排队或运行，请联系管理员处理后重试”，不得把该错误描述为自动取消中、等待中或普通未知失败。

## 8. 删除范围

### 8.1 必须删除的数据库记录

以删除前冻结的目标 ID 集合为准，显式盘点并删除：

1. `Video`。
2. 当前 `Annotation`、legacy `Review`、legacy `Clip`。
3. `Submission`、`SubmissionAnnotation`、绑定 Submission 的 `Review` 与 `Clip`。
4. 仅被目标视频 Submission 使用的 `DetectionSnapshot`、`DetectionSnapshotState`。
5. `DetectionImport` 及其 `RawDetection`、`DetectionStateOverride`、`DraftIdentityEdit`、`DraftDetectionChange`。
6. 迁移兼容表：`CorrectedTrack`、`CorrectedDetectionAssignment`、`IdentityEdit`、`DetectionSuppression`、`SuppressionDetection`。
7. `VideoImportBatch.created_video_id` 指向目标视频的批次记录；不只将外键置空。
8. 所有非 `queued/running` 关联媒体任务和关联项目导出任务的 `BackgroundJob` 记录；如发现活动关联任务，则整次删除在任何清理前拒绝。

删除顺序由专用服务和受严格约束的权威删除通道控制，不依赖 ORM cascade；正常业务路径的不可变保护不被削弱，删除结束后所有 authority triggers 仍存在且有效。

若同一 `DetectionSnapshot` 意外被其他视频引用，删除必须拒绝并报告完整性冲突，不得级联破坏其他视频。

### 8.2 必须删除的实体文件

- `videos_dir` 中目标 `Video.storage_path` 对应的原视频；
- `detection_imports_dir` 中目标导入的 `tracks_path`、`metadata_path`；
- 目标 `VideoImportBatch` 的 `video_path`、`tracks_path`、`metadata_path` 等数据库路径字段所引用的文件：`video_path` 按 `videos_dir` 受控根解析，`tracks_path/metadata_path` 按 `detection_imports_dir` 受控根解析；当前 `import_batches_dir` 没有实际批次文件，不扫描或依赖该未使用目录；
- `clips_dir` 与 `thumbnails_dir` 中所有目标 Clip 文件；
- 任何包含目标视频冻结 Submission 的项目导出 ZIP；
- 非活动关联任务（已知终态仅为 `succeeded/failed/cancelled`）留下的结果文件、staging、临时 ZIP 或任务临时源文件。

所有路径必须先通过既有受控根目录解析规则；禁止跟随越界路径、目录目标或不可信 symlink。相同实体路径须去重后只删除一次。路径为空或文件本来不存在可记为“已清理”，越界路径必须视为安全错误而不是直接删除。

目录类型的 staging/临时产物在 POSIX 上使用 descriptor-relative、`O_NOFOLLOW` 的遍历、purge 与 restore，并逐级复核冻结 identity，避免路径替换和 symlink 竞态。缺少所需 dir-fd/no-follow 能力的平台不得退化为按路径递归删除或恢复：涉及目录时必须 fail closed；普通文件仍按受控根、相对 key 与冻结 identity 处理。生产部署前必须核对 Linux 提供该目录安全能力，并保持单 Uvicorn worker。

### 8.3 不删除的内容

- 项目、成员、类别方案和类别审计；
- 其他视频及其数据库记录和实体文件；
- 不含目标视频的媒体/导出任务和 ZIP；
- 全局 cleanup 任务与清理问题日志。

## 9. 关联任务处理

### 9.1 任务识别

删除开始时，在同一冻结视图内解析：

- legacy media payload 的 `video_id`；
- Submission media payload 的 `submission_id/submission_annotation_ids`；
- export payload 的 `submission_ids/submission_annotation_ids/refs`；
- 已成功 export 的冻结 payload，用于判断其 ZIP 是否包含目标视频。

不能只按 `project_id` 删除任务；项目导出可能只包含其他视频。识别结果必须同时记录任务当前状态，并严格区分 `queued/running` 活动任务与 `succeeded/failed/cancelled` 非活动终态。任何不在这五个已知值内的状态都必须 fail closed，以 409 零副作用拒绝删除并提示联系管理员，不得猜测为非活动状态。

### 9.2 活动任务门禁（已确认）

- 只要发现任何与目标视频关联的 `queued` 或 `running` 任务，本次删除即返回 409。
- 只要发现任何关联任务状态不是已知的 `queued/running/succeeded/failed/cancelled`，同样 fail closed 返回 409。
- 拒绝时不得自动取消或修改任务状态，不得等待 worker，不得创建删除清单，不得移动或删除目标文件、任务文件或任何业务数据。
- 错误响应和前端提示必须说明关联任务仍在排队或运行，并提示用户联系管理员解决；管理员处理后，待活动关联任务不存在，用户可重新发起完整删除请求。
- 删除独占门禁必须覆盖关联任务创建/入队路径，防止活动任务检查通过后又有新任务入队；最终删除事务提交前仍须复核不存在 `queued/running` 关联任务，复核失败则回滚并返回 409。

### 9.3 非活动任务清理

- 仅在确认不存在活动或未知状态关联任务后，删除 `succeeded/failed/cancelled` 非活动关联任务记录及其结果文件、ZIP、staging 和临时产物。
- 非活动项目导出的冻结集合只要包含目标视频，其整项任务记录和 ZIP 都纳入删除范围；不得保留一个缺少目标视频的缩水 ZIP。
- 不含目标视频的任务及其文件保持不变。

### 9.4 不等待与 worker 一般一致性

删除流程不需要 worker 协作取消协议，不等待或终止 ffmpeg/ZIP 子进程，也不通过删除任务行迫使运行线程报错。此决定不削弱 worker 自身的一般一致性：worker 仍须按现有任务协议正确 claim、复核状态、原子发布并写回终态，不能重复发布或以错误状态覆盖终态。

**强不变量**：job 一旦进入 `succeeded`、`failed` 或 `cancelled` 非活动终态，任何 worker 此后都不得再为该任务创建、替换、删除文件，也不得再创建、更新或删除该任务的任何数据库记录。当前实现与测试已保证该终态静止不变量，删除流程据此把非活动任务及其文件纳入清理范围。

## 10. 并发与一致性

本规格的生产安全前提是 Uvicorn 仅运行单个应用进程，即 `--workers 1`，删除与任务入队可复用同一进程内独占门禁。若未来改为多个 Uvicorn worker、多个应用进程或多实例部署，进程内锁不再充分；必须先将删除、同视频写入及关联任务创建/入队切换到数据库锁、分布式锁或其他可证明的跨进程门禁，再允许启用本删除功能，不得直接沿用本规格的进程内门禁上线。

1. 删除必须与同视频标注 CRUD、检测替换、track 修正、提交、撤回、审核、媒体生成和分配写操作竞争同一独占门禁。
2. 获取门禁后重新读取权限、项目归属、工作流状态、Submission、任务和路径集合；门禁外预检只能用于快速失败。关联任务创建/入队必须受同一门禁约束，防止活动任务检查后新任务入队。
3. 第二个删除请求不得重复执行；首个未完成时返回 409，首个成功后返回 404。
4. worker 任何最终发布都必须验证其 job 仍为 `running`、仍持有有效 claim 且冻结 payload 未变；终态任务不得被后续 worker 写回覆盖或重复发布。该一般一致性要求独立于删除流程，删除流程不负责协作取消 worker。
5. 删除成功后，流媒体、标注、审核、片段和任务接口均不得再返回目标视频数据。
6. 最终短数据库事务必须再次复核不存在 `queued/running` 或未知状态关联任务；若发现则回滚，按删除清单恢复此前已隔离文件并返回 409，不删除业务数据。

## 11. 失败恢复策略（已确认）

数据库与文件系统无法共同原子提交。采用**受控隔离目录 + 删除清单**：

1. 获取独占门禁，预检并在内存中冻结数据库 ID、文件 identity 与规范化路径；
2. 在写入删除清单和移动任何文件前检查活动或未知状态关联任务；存在 `queued/running` 或未知状态任务则返回 409，且不写清单、不改变任务、不移动文件、不删除业务数据；
3. 不存在活动或未知状态关联任务时，将冻结内容写入同一数据盘的删除清单，再把可控文件原子移动到删除隔离目录；任一写入或移动失败则恢复已移动文件，数据库不变；
4. 在短 `BEGIN IMMEDIATE` 内再次复核不存在活动或未知状态关联任务，再通过专用删除通道删除全部关联记录，执行外键检查与残留计数后提交；复核失败则回滚、恢复已移动文件并返回 409；
5. 提交后物理删除隔离目录；全部成功后删除清单并返回 204；
6. 若数据库提交失败，按清单恢复文件；若数据库已提交而最终 unlink 失败，由启动恢复/运维命令继续清除隔离目录，不得把数据库记录伪造回来。

删除清单是文件系统恢复工件，不是数据库字段；不得包含凭据，路径只记录受控相对 key 与文件 identity。

采用受控隔离目录 + 删除清单与**严格同步**成功语义：隔离目录物理清空后才返回 204。数据库已提交但最终 unlink 失败时返回 500，错误明确说明业务数据已删除、实体残留将由恢复器继续清理；客户端不得把该结果解释为“视频仍存在”并反复创建同 ID 请求。启动恢复或运维命令必须按清单继续清理，不能伪造恢复已删除的数据库记录。

当前实现使用版本化、原子替换写入的 manifest 记录 operation、阶段、冻结数据库 ID、终态任务 ID、受控相对 key 与文件 identity。应用启动时先于媒体/导出 worker 执行 quarantine recovery：数据库对象仍存在则按清单 restore，已删除则继续 purge；恢复结果不安全或无法确定时启动 fail closed，要求管理员介入。

## 12. 可观测性与审计边界

- 因为是硬删除且不新增数据库字段，成功后不保留目标视频业务审计行。
- 应在应用日志记录操作者用户 ID、项目 ID、视频 ID、开始/结束时间、阻断删除的活动任务 ID/状态、已清理的非活动任务 ID、各类删除计数、最终阶段和错误摘要；禁止记录 token、绝对敏感路径或文件内容。
- 文件隔离、恢复和删除失败由独立版本化删除 manifest 记录并交由启动恢复处理；应用日志只记录安全摘要。
- API 错误不得暴露服务器绝对路径、SQL 或命令行详情。

## 13. 验收标准与证据路径

### 13.1 权限与状态矩阵

- active owner/admin 可删除 `draft/rejected` 视频；其他角色、inactive 成员、跨项目请求及其他工作流状态均失败且零副作用。
- 状态在确认框打开后变化时，后端按最新状态重新判断。

### 13.2 数据库完整性

- 构造同时含 Annotation、多个导入修订、draft edit、Submission 全生命周期、Review、Clip、批次和任务的视频；删除后逐表断言无目标关联行。
- 运行 `PRAGMA foreign_key_check` 无结果；正常不可变 trigger 在删除后仍能拒绝违规 UPDATE/DELETE。
- 同项目其他视频与共享类别、成员、项目审计的行数和关键摘要不变。

### 13.3 文件完整性

- 对各受控目录建立明确文件清单；删除后目标文件、关联 ZIP、staging 和临时文件均不存在，其他视频文件 SHA-256 不变。
- 文件缺失、重复路径、越界路径、symlink、目录目标、权限不足和 unlink 失败均有专项测试。

### 13.4 任务竞争

- queued media、running media、queued export、running export 均返回 409；逐项断言任务状态不变、无等待、无自动取消、未写删除清单，且目标文件、任务文件和业务数据均未移动或删除，响应提示联系管理员处理。
- 通过可控 worker barrier 和入队竞争分别在“活动任务检查前后”“claim 后”“ffmpeg 后”“ZIP 发布前”触发删除，证明独占门禁能阻止检查后新任务入队，最终事务会复核活动任务，忙时删除保持零副作用。
- `succeeded/failed/cancelled` 非活动 media/export 任务不阻断删除，其任务记录、结果文件、关联 ZIP、staging 与临时产物均按删除范围清理；构造未知状态时必须 409 且零副作用。
- 在 job 写入 `succeeded/failed/cancelled` 后继续触发 worker 各阶段，断言 worker 不再创建、替换、删除或写回该任务的任何文件或数据库记录，证明删除依赖的终态静止不变量成立。
- 非活动多视频导出含目标视频时整项任务记录和 ZIP 被清理；不含目标视频的并行任务保持不变。
- 管理员处理活动任务且不再存在 `queued/running` 关联任务后，重试删除可按正常路径完成。

### 13.5 恢复故障注入

- 在文件隔离前后、数据库提交前后、最终 unlink 前后注入故障，验证恢复结果与所选成功语义一致。
- 重启恢复可从删除清单确定性完成或回滚，不依赖人工猜测。
- 同一删除请求在可重试失败后再次执行，不产生越界删除或重复任务发布。

### 13.6 前端流程

- 权限可见性、分状态确认文案、普通危险确认、loading、失败保留、成功刷新与键盘焦点均通过组件测试和人工浏览器验收。
- 删除成功后从视频库、分配统计、审核队列和片段库同步消失。

### 13.7 本地实现验证

- DELETE API 集成测试覆盖 204 成功、权限/工作流拒绝、重复删除、同视频 gate 冲突、活动或未知任务 409 零副作用、数据库冲突恢复及提交后 purge 恢复。
- 数据库与文件系统专项测试覆盖完整外键图、authority trigger 恢复、终态任务清理、manifest/quarantine/startup recovery、路径越界与 symlink 拒绝；POSIX descriptor-relative 目录 purge/restore 由支持平台测试覆盖，缺少能力平台验证目录操作 fail closed。
- worker 与任务识别测试覆盖终态静止不变量、关联任务分类及入队/删除共用 gate；帧权威迁移、API、Submission、媒体与导出回归通过。
- 前端 production build 通过，统一选择操作栏、仅删除符合条件项、危险确认、逐项结果汇总、409/404 处理及成功项移除已完成代码级验证；尚未部署，生产环境与人工浏览器验收不在本地自动化结论内。

## 14. 实现状态与部署门禁

删除功能产品决策已全部确认：

1. active `owner/admin` 可删除，不受视频负责人限制。
2. 仅允许 `draft/rejected`；`submitted/approved` 必须拒绝。
3. 任一 `queued/running` 或未知状态关联任务都会以 409 阻断删除，提示联系管理员；不自动取消、不等待、不改变任务状态，也不移动或删除任何目标文件/业务数据。活动及未知状态任务不存在后可重试；已知非活动终态仅为 `succeeded/failed/cancelled`，其任务及结果文件照常清理。
4. 使用受控隔离目录 + 删除清单；只有数据库记录与实体文件都清理完成才返回 204。
5. 使用普通危险确认，不要求输入文件名。
6. 生产仅允许单 Uvicorn 应用进程 `--workers 1`；多进程或多实例上线前必须先实现可证明的跨进程门禁。
7. worker 必须保证 job 进入 `succeeded/failed/cancelled` 后不再改变该任务的任何文件或数据库记录。

上述 DELETE API、权限/状态检查、关联任务零副作用门禁、单进程 gate、终态 worker 不变量、manifest/quarantine/startup recovery 与视频库 UI 入口均已实现并完成本地验证。目录 purge/restore 的安全实现限定为 POSIX descriptor-relative 能力；缺少该能力的平台对目录操作 fail closed。生产仍必须使用单 Uvicorn worker，且本状态不表示已部署。

同一 worktree 还已实现帧权威链路：`start_frame/end_frame` 双端 inclusive，要求 `end_frame > start_frame`，时间只由帧与 FPS 派生，并由 API、数据库约束、Submission、媒体和导出复用；详细契约仍由《标注流程与帧边界需求规格》维护，不与删除策略隐式绑定。
