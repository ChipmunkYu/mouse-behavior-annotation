# 低码率展示代理视频实现计划

> **状态：P1 代理生成能力已在独立分支本地实现并通过聚焦验证，尚未推送、尚未部署，能力默认关闭。** 当前生产基线仍为 `8ecb98f`：Preview 已使用原生 HTTP Range，Clips、Review、Annotate 仍使用 legacy Blob。本文按方案1收敛后续目标：四个展示入口统一“一次性完整下载低码率代理 + Blob URL 播放”。现有 Preview Range 能力可以保留在代码或回滚制品中，但不属于本计划的生产目标。

## 1. 目标与边界

### 1.1 明确目标

1. 为每个可展示 `Video` 异步生成独立、可验证、可版本化的低码率 H.264 MP4 代理。
2. Preview、Clips、Review、Annotate 统一使用 Fetch API 完整 GET 同一个代理资源；完整响应经 `response.blob()` 后创建 `URL.createObjectURL()`，再交给 `<video>`。
3. 四入口复用 `frontend/src/media/` 中同一个 controller/hook；统一下载进度、取消、错误和 Blob URL 生命周期，不在页面复制状态机。
4. 后端 stream/download 统一经过代理 resolver，四入口读取同一个 ready 代理；代理缺失、失败、越界或损坏时严格报错。
5. 建立原片身份、持久化任务、上传/导入同事务入队、显式 backfill、磁盘保护、删除清理、恢复和失败重试的完整生命周期。
6. 在 P0 用真实样本锁定编码 profile 和完整下载体验，不能把候选参数或容量估算直接当成上线承诺。

### 1.2 方案1的含义与限制

- 这是**完整下载后播放**，不是 HTTP Range 按需播放，也不是边下边播。前端只有在完整响应成功并创建 Blob URL 后才进入可播放状态。
- 本计划不把 Preview 的 HTTP Range 迁移到 Clips、Review、Annotate，也不把 ticket GET/HEAD/Range 定义为目标契约。现有 Range 路线可保留用于显式回滚，但生产方案1前端不依赖 Range。
- 若 20 分钟代理约 600 MB，则完整下载等待约为：`0.7 MB/s ≈ 14 分 17 秒`、`1 MB/s ≈ 10 分钟`、`5 MB/s ≈ 2 分钟`。本方案**不解决低带宽下的首次等待**。
- 优势是实现和行为一致；完整下载后，seek、逐帧和倍速播放不再依赖网络质量或服务端 Range 行为。
- 大 Blob 会占用浏览器内存，并可能受到浏览器临时磁盘、Blob 存储配额和系统内存压力影响，必须在 P0 与浏览器验证中量化。

### 1.3 非目标

- 不引入 HLS、DASH、CDN、H.265/HEVC、多档自适应码率或分片缓存。
- 不替换或重新编码 `Video.storage_path` 指向的原片。
- 不改变片段精确重编码、Submission 冻结、导出、缩略图或标注数据契约。
- 不在应用启动时扫描全部历史视频并无限回填。
- 不把 Annotate 现有独立 `useBlocker` 白屏问题混入本计划；该问题仍是 Annotate 验收前置项。

## 2. 术语与权威不变量

| 术语 | 定义 |
|---|---|
| 原片 | 上传或三文件导入后落入原片目录、由 `Video.storage_path` 指向的不可替代媒体源 |
| 展示代理 | 从原片派生的低码率 MP4，仅供 Preview、Clips、Review、Annotate 展示 |
| 完整下载 | Fetch API 等待完整响应，调用 `response.blob()` 后才创建 Blob URL |
| ready | DB 状态、profile、source SHA-256 和代理实体一致，且发布验证已通过 |

以下不变量必须由实现、数据库约束和测试共同锁定：

1. `Video.storage_path` 只表示原片，代理任务、resolver、backfill、删除和清理都不得改写它；替换媒体必须创建新 `Video`。
2. 代理使用独立字段、独立目录和独立 resolver；禁止用含混的“当前播放路径”复用原片路径。
3. 片段生成的 `resolve_input_path()`、Submission 的冻结身份与 `stage_submission_input()`、缺失片段补生成及项目导出始终读取原片。
4. Submission 保存的路径、SHA-256、大小及文件身份均针对原片；代理更新不得改变已冻结 Submission。
5. 代理不得改变标注帧索引、帧数、帧率和时间轴语义。降分辨率与压缩不能造成叠加漂移或首尾帧丢失。
6. `source_sha256` 是原片权威内容身份；生成代理前必须计算完整 SHA-256，ready 的 `display_source_sha256` 必须等于它。
7. `Video.status` 继续表示上传媒体状态，不得复用为代理状态。
8. 严格模式下，代理 pending、failed、缺失、越界、损坏或 profile/hash 不匹配均显式失败，不能静默回退原片。仅迁移或事故期间允许显式、默认关闭、可审计的整体回滚。

## 3. 统一播放与资源选择契约

### 3.1 四入口前端契约

四入口采用同一流程：

1. controller 根据当前 video/surface 发起带现有认证的完整 GET，并创建本次请求专属 `AbortController`。
2. 共享下载 helper 读取 `Content-Length`（若存在）并显示预计总量；基线实现直接等待 `response.blob()`，Fetch API 本身不提供可靠的增量下载进度回调。
3. 若 P0 确认必须显示实时百分比，则改用 `response.body.getReader()` 计数字节并在完整接收后通过 `new Blob(parts)` 组装；响应体被 reader 消费后不能再次调用 `response.blob()`。两种实现必须在 P0 比较峰值内存后选定其一，完成前都保持“下载中”，不得提前创建 Blob URL 或进入可播放状态。
4. 完整 Blob 成功后调用 `URL.createObjectURL(blob)`，再把 URL 交给 `<video>`；媒体错误由 controller 统一归类。
5. 切换视频、关闭弹窗、页面卸载或新请求取代旧请求时，先 `abort()` 未完成下载；对已创建 URL 执行 `URL.revokeObjectURL()`，清空 video source/Blob 引用，防止旧响应晚到覆盖新状态。
6. controller/hook 只允许一个活动请求和一个当前 object URL；页面只负责接线和展示统一状态，不复制下载、重试、取消或释放逻辑。

下载进度不是“可播放进度”。UI 必须明确“正在完整下载，下载完成后才能播放”，并提供取消/重试。P0 应确定是否需要展示预估剩余时间；不得以不稳定估算制造已可播放的误解。

### 3.2 后端代理 resolver

- 保留现有认证、项目成员权限和实时授权；认证方式不能决定媒体资源。
- 授权 helper 返回 `Video`，统一 display resolver 校验 `display_status`、profile、source hash、相对路径、代理根目录边界、普通文件和非空实体。
- Preview、Clips、Review、Annotate 的完整 GET 都调用该 resolver，并读取同一个代理文件。不能出现 Preview 读代理而其他入口仍读原片。
- 目标契约只要求完整 GET；不把 ticket HEAD/Range、206、续票或多段 Range 作为方案1验收项。底层 `FileResponse` 即使保留 Range 能力，方案1前端也不得依赖。
- `pending/processing` 返回脱敏 `409 + DISPLAY_PROXY_PENDING`；`failed`、缺失、损坏或 profile/hash 不匹配返回脱敏 `409 + DISPLAY_PROXY_FAILED`。不存在/无权访问保持既有 404/403，避免泄漏资源存在性。
- 响应文件名固定为脱敏 `.mp4`（如 `display-video-{id}.mp4`），不得泄漏用户文件名或磁盘路径。
- 发布时完成内容与媒体验证；每次 GET 不重复执行整文件 hash、ffprobe 或逐帧校验。发布后损坏由有界 reconciliation 标记 failed。

## 4. 数据与文件模型

候选迁移 `backend/migrations/versions/0016_display_proxy.py` 在 `videos` 增加：

| 字段 | 候选类型/值 | 用途 |
|---|---|---|
| `display_path` | nullable `String(512)` | 代理根目录下安全相对路径，仅 ready 可用 |
| `display_status` | `pending / processing / ready / failed` | 独立代理状态 |
| `display_error` | nullable `Text` | 截断、脱敏的最近错误 |
| `display_profile_version` | nullable `String(64)` | 已发布代理 profile |
| `source_sha256` | nullable `String(64)` | 原片完整 SHA-256；新建生产 Video 必填 |
| `display_source_sha256` | nullable `String(64)` | 本次代理对应的原片 SHA-256 |
| `display_generated_at` | nullable datetime | 审计和排障时间，不单独证明 ready |

v1 每个 `Video` 只维护一组 display 字段，不引入多 profile 资产表。数据库 CHECK 要求状态枚举有效；ready 时 path/profile/display source hash 非空、error 为空且两个 source hash 相等，非 ready 时清空 ready 资产字段。路径还需基础 CHECK，应用 resolver 继续负责规范化、代理根目录和 symlink 边界。

迁移可用 `server_default='pending'` 兼容既有插入；历史 `source_sha256` 先为空。迁移本身不扫描原片、不入队，历史数据必须先显式 hash backfill，再显式代理 backfill。SQLite upgrade/downgrade 必须验证，downgrade 不得损伤原片及项目、标注、Submission、Clip、export 数据。

代理位于独立配置目录（候选 `data/display_proxies/`），不得与原片、片段、导出混放。DB 仅保存根目录下相对路径；最终名包含 video ID、source hash 摘要和 profile version，并使用安全字符白名单，不拼用户文件名。

## 5. 编码 profile：P0 后锁定

### 5.1 暂定 profile，P0 实测后锁定

- 分辨率固定为 `1280×720`；当前按输入均为 16:9 处理。若后续出现其他宽高比，必须明确采用保持比例并加黑边等规则，禁止直接拉伸画面。
- MP4 + H.264/`libx264`，`-crf 28`、`-preset veryfast`、`yuv420p`。
- 固定 GOP 30 帧：`-g 30 -keyint_min 30 -sc_threshold 0`，即关闭 scene cut 额外插入关键帧。按项目视频 30 fps 计算，每 1 秒一个关键帧。
- 显式 `-map 0:v:0 -an`，不保留音频；使用 `-movflags +faststart`。
- 保留 `-vsync 0` 作为暂定时间轴参数，但不得强制使用 `-r 30` 改写输入帧率。

候选命令形态如下，实施时必须使用参数数组而不是 shell 字符串：

```text
ffmpeg -y -i INPUT -map 0:v:0 -an -vf scale=1280:720 \
  -c:v libx264 -preset veryfast -crf 28 -pix_fmt yuv420p \
  -g 30 -keyint_min 30 -sc_threshold 0 -vsync 0 \
  -movflags +faststart -f mp4 TEMP_OUTPUT
```

2026-08-28 人工视觉检查记录：使用秋采数据9鼠样本开头300帧生成约10秒、1280×720、H.264/libx264、CRF 28、`veryfast`、固定30帧GOP、无音频的代理视频；用户确认该候选画质不影响人眼识别小鼠。此结论通过当前候选的主观清晰度门禁，但不替代其余样本、时间轴、容量、完整下载、浏览器资源和并发实测，也不表示功能已经实现。

上述参数仍须经 P0 对秋采数据、短视频、异常时间轴样本和约 2 GB 原片实测后版本化锁定。P0 必须确认所有支持输入符合目标 30 fps 语义，并证明固定 GOP、`-vsync 0` 和缩放没有改变帧数、PTS、首尾帧或标注叠加关系。

“20 分钟约 600 MB”仅是按平均 `4 Mbps` 计算的容量示例（约 600 MB 十进制），不是 CRF 输出大小、网络速度或最终产品承诺。P0 必须记录各样本实际 P50/P95 码率和大小。

### 5.2 发布门禁

ffmpeg 使用参数数组、禁止 `shell=True`，输出同文件系统内唯一 `.part` 临时文件。完成后验证：

- ffprobe：容器、codec、pix_fmt、单视频流、无音频、尺寸、时长；
- 解码/逐帧：frame count、首尾帧、PTS/`best_effort_timestamp_time` 和画面指纹映射；
- 文件：非空、内容摘要、profile/source 身份一致；
- 发布：temp 写入并 fsync，`os.replace()` 原子替换，fsync 父目录，再用 CAS 提交 DB ready。

无法保持受支持输入时间轴/帧语义的候选不能上线；不得静默接受偏差。

## 6. `BackgroundJob` 与单 owner

- 新增 `job_type='display_proxy'`，不改变既有 `media` 和 `export` 任务语义。payload 至少冻结 `video_id`、`project_id`、`profile_version`、`source_sha256`，不记录路径、票据或密钥。
- dedupe key 候选为 `display-proxy:video:{id}:source:{sha256}:profile:{version}`。活动任务依靠 dedupe，永久幂等以 Video ready 字段和已验证实体为准。
- 独立 `display_proxy_jobs.py` worker 负责领取、转码、验证和发布；不要把它塞入片段 worker。
- 领取使用条件更新；ffmpeg 前后、发布前和 ready 提交前重读 Video，并用状态/source/profile/job ownership CAS 防止旧 worker 覆盖新状态。
- attempt 上限、指数退避和人工 retry 在 P1 锁定。确定性错误不得热循环；显式 retry 必须产生可追踪 attempt。
- 并发有硬上限，并与片段/export 共享 CPU、内存和 I/O 预算。P0/P1 用 5 并发压力测试决定生产值，不默认把生产并发设为 5。
- v1 只支持单应用实例、单 Uvicorn worker owner。部署、恢复和回滚不得出现新旧实例或双 owner 并存。

启动只恢复 DB 已有 queued/running 任务，不扫描全部 Video。中断的 running 任务按 ownership 清理自身 temp，再依 attempts CAS 回 queued 或 failed；processing 且无活动任务的 Video 由有界 recovery 对账，不能从文件名推断 ready。

## 7. 入队、backfill 与磁盘保护

### 7.1 新 Video 原子入队

- multipart 上传：原片原子落盘并计算完整 SHA-256 后，在创建 `Video(storage_path=原片)` 的同一 DB 事务插入 queued display job；commit 后只唤醒 worker。
- 三文件导入：仅在完成接口真正创建 Video 时，同事务写 source hash、pending 状态和 queued job；合法 `video_only` 同样处理。未创建 Video 的 unfinished batch/cancel 不产生代理任务。
- metadata create 若是生产 Video 写口，也必须满足原片稳定、hash 完整和同事务入队，不允许调用方日后替换 `storage_path`。
- 静态搜索与测试覆盖所有生产 `Video(...)`/`storage_path` 写口；seed/dev 与测试 fixture 只能显式白名单。

### 7.2 显式 backfill

运维 CLI 支持 `--dry-run`、稳定游标/`--batch-size`、项目或视频过滤、最大任务数、`--profile-version` 和显式 `--retry-failed`。dry-run 报告候选数、源字节、预计代理空间及状态分布，不修改 DB/文件；生产按批准的小批次执行，可暂停续跑。

历史数据先分批计算 `source_sha256`，再分批入队代理。应用启动不得自动无限 backfill。

### 7.3 磁盘保护

- 配置独立 reserve bytes；任务开始前按候选 profile 估算，发布前重新检查。
- 捕获 ENOSPC，清理本任务 temp、保留原片、任务置明确 failed；不得产生 ready 空文件或静默改用原片。
- backfill、实时上传、片段和导出共享容量/吞吐观测；超过阈值时暂停新代理任务，而不是侵占原片或业务产物空间。

## 8. 删除、清理与恢复

- 扩展视频硬删除 manifest/quarantine/recovery，将代理作为与原片分离的受管实体。删除计划与执行均校验代理根目录和文件身份。
- `related_video_jobs` 识别 display job 的 payload/dedupe/result/temp 引用。queued/running 任务存在时按保守模型返回 409，不在 v1 实现运行中取消。
- 可删除时，原片与代理分别隔离后再提交 DB 删除；失败按 manifest 恢复。删除完成后的新下载必须 404。
- RetentionCleaner 有界处理过期 `.part`、无 DB 引用的 orphan 和旧 profile；默认 dry-run/报告优先，不从文件名推断归属或 ready。
- 当前 ready、活动任务、quarantine/recovery 管理中的文件不得作为普通孤儿删除；任何清理都不得触及 Submission 原片、Clip 或 export。
- 覆盖 replace 成功但 DB 失败、DB ready 后文件缺失、转码中进程退出、删除中断等窗口。最坏结果只能是代理不可用并显式失败/待清理，不能损伤原片或让旧代理冒充当前版本。

## 9. 前端内存与取消控制

统一 media controller/hook 至少暴露：`idle / downloading / ready / pending / failed / cancelled`，以及下载字节、总字节、错误分类和当前 object URL。具体命名可按现有状态模型调整，但语义必须集中。

重点控制：

- 流式读取响应用于进度时，不得无界复制 chunk；最终组装 Blob 的峰值 JS heap、浏览器 Blob 存储与临时磁盘占用必须实测。
- 切换视频立即 abort；旧 Promise 即使随后 resolve，也必须通过 request generation/token 拒绝提交状态。
- 每个创建成功的 object URL 恰好 revoke 一次；新 URL 替换旧 URL 前先清理 video 引用和旧 URL。
- HTTP/解析/代理状态/用户取消分开归类；用户取消不显示为代理生成失败。
- 重试创建新 AbortController，不复用已 aborted signal；页面卸载清理必须幂等。
- 约 600 MB Blob 在多个标签页或多个入口并存可能造成倍增占用。P0 若证明目标浏览器无法稳定承载，应阻断方案1上线，而不是暗中改回 Range。

## 10. P0—P4 实施阶段

| 阶段 | 主要内容 | 完成门禁 | 回滚 |

## 11. 验证计划

### 11.1 必测矩阵

1. **不同网速完整等待**：对约 600 MB 代理限速到 0.7、1、5 MB/s，验证约 14:17、10:00、2:00 的量级、进度准确性、完成前不可播放及超时策略；不得宣称解决低带宽首次等待。
2. **约 2 GB 原片转码**：生成 600 MB 候选并记录实际大小、平均/P95 码率、转码耗时、CPU、RSS、I/O 和磁盘峰值；若不接近 600 MB，按实测报告而非调整口径。
3. **浏览器完整字节数**：四入口记录响应 Content-Length/实际累计字节/Blob.size，三者在协议允许范围内一致；确认不是 Range、不是 206 拼接、不是远端 URL 直播。
4. **JS/Blob 资源占用**：Chrome/Edge/Firefox 记录下载中与完成后的 JS heap、进程 RSS、Blob/临时磁盘、关闭后回收，以及多次切换和多标签页压力。
5. **切换取消**：下载中切换/关闭/卸载必须中止网络；旧响应不污染新状态；已创建 URL 均 revoke，重复切换无持续增长。
6. **四入口代理指纹**：原片和代理放置可区分容器/帧指纹；Preview、Clips、Review、Annotate 的完整 GET 字节和解码帧均匹配同一代理，服务端审计显示 resolver 打开代理根目录实体。
7. **原片权威产物**：实际生成片段、冻结 Submission、补生成片段并导出，指纹/SHA-256 证明全部来自原片，`storage_path` 及原片身份不变。
8. **时间轴与帧**：覆盖秋采数据、CFR、VFR、非零/负起点、timestamp discontinuity、B frame、极短视频；逐帧比较 PTS、`best_effort_timestamp_time`、frame count、首尾帧和叠加对齐。
9. **5 并发转码**：同时处理 5 个代表性视频，并行执行在线下载、片段与导出，量化 API P95、CPU、RSS、I/O wait、失败和退避，据此锁定并发。
10. **删除/ENOSPC/recovery**：覆盖活动任务删除 409、发布前后 kill、replace/DB 窗口、stream 中删除、真实 ENOSPC、temp/orphan 清理、重启恢复和二次恢复幂等。
11. **严格失败**：pending、failed、缺文件、坏文件、旧 profile/hash 不匹配时四入口均显示脱敏错误，服务端无原片展示读取，回退命中为 0。

### 11.2 自动化与构建门禁

- 后端：迁移 upgrade/downgrade、状态 CHECK、resolver、任务 CAS/dedupe/retry、上传/导入事务、backfill、删除/cleanup/recovery、片段/Submission/export 权威测试、全量 pytest 和 compileall。
- FFmpeg：使用部署锁定版本做真实集成测试；Fake processor 只验证编排，不能替代媒体证据。
- 前端：controller/hook 的进度、完整后 ready、AbortController、晚到响应、重试、object URL 创建/释放测试；四 surface 集成测试和 production build。
- 日志只记录 request/job/video/project ID、profile、hash 摘要或匹配布尔值、状态、耗时、字节和错误类别；不得记录 Authorization、Cookie、ticket、完整 URL、完整 hash、绝对路径或未清洗 stderr。

## 12. 切换与回滚

1. 先部署 schema、目录、worker、backfill、resolver 和观测能力，但生产展示仍保持当前基线，不能称为代理已上线。
2. 新视频持续入队，历史数据经批准后显式小批回填；完成 ready 覆盖和 P0/P1/P2 证据。
3. 预生产一次性验收四入口完整 Blob 下载。Preview 的现有 Range 能力不作为依赖，也不向其他入口迁移。
4. 在 `active display job = 0`、旧进程完全停止、能力版本一致的单实例维护窗口切换四入口；禁止滚动发布和双 owner。
5. P4 生产严格模式只读代理，异常显式报错。

迁移期可保留一个默认关闭、显式启用、可审计的全局原片回滚开关，或保留 `8ecb98f` 对应的 Range/legacy 回滚制品。它只用于预生产或事故整体回滚，不得按页面长期混用；只要启用，就不得宣称“严格代理完成”。最终 P4 关闭并移除或封死该开关。

回滚不得写回或改写 `Video.storage_path`。已生成代理可隔离保留待排查，确认无 DB、活动任务、manifest 或 recovery 引用后再清理。

## 13. 主要风险与控制

| 风险 | 控制 |
|---|---|
| 完整下载首次等待过长 | 明示等待模型和进度；P0 限速实测；不宣称低带宽优化 |
| 大 Blob 导致内存/临时磁盘压力 | P0 浏览器量化、单活动请求/URL、及时 abort/revoke；超预算则阻断上线 |
| 代理改变帧/时间轴 | 逐帧 PTS/画面映射与叠加验收；`-vsync 0` 不是充分条件 |
| 代理误作业务权威源 | 字段/目录/helper 分离，片段/Submission/export 指纹门禁 |
| 回填或转码挤满磁盘 | dry-run、reserve guard、小批 backfill、ENOSPC fail closed |
| ready 与实体不一致 | temp 验证、fsync、原子 replace、DB CAS、reconciliation |
| 删除与晚到 worker 复活文件 | 活动任务删除 409、ownership CAS、manifest/quarantine/recovery |
| 页面实现分叉 | `frontend/src/media/` 单一 controller/hook，页面仅接线 |

## 14. 完成定义（DoD）

- P0 已用真实数据锁定 profile v1；“约 600 MB”已由实测替代估算口径，支持输入和浏览器资源上限明确。
- `storage_path` 与 display 字段/目录/resolver 分离，原片不可替换；source/display SHA-256 和 ready CHECK 生效。
- multipart、三文件完成和其他生产 Video 写口均在同一事务创建 queued job；历史仅通过显式 hash + proxy backfill。
- worker 的 dedupe、CAS、单 owner、retry、5 并发、ENOSPC、临时文件原子发布和崩溃恢复通过。
- 删除、cleanup、orphan、manifest/quarantine/recovery 覆盖代理，且不损伤原片、Submission、Clip 或 export。
- 四入口均通过统一完整 GET 读取同一 ready 代理；浏览器累计字节等于完整代理，下载结束后才创建 Blob URL 和进入 ready。
- controller/hook 统一进度、取消、晚到响应保护、错误和 object URL 生命周期；页面没有复制状态机，切换/卸载后资源可回收。
- 四入口代理指纹通过；片段生成、Submission 冻结及导出原片指纹通过；时间轴、帧数、首尾帧和标注叠加通过。
- 生产不依赖 HTTP Range，不以向其他入口迁移 Range 作为任务或验收项；低带宽首次等待限制已明确披露。
- P4 下 pending/failed/missing/corrupt/profile/hash 异常均严格报错，无静默原片回退；迁移期开关关闭或封死。
- 单实例维护切换与整体回滚演练通过，日志/附件无票据、Cookie、Authorization 或敏感路径。
- 在完成上述证据前，只能表述为“P1 本地候选已实现、整体方案尚未完成且未部署”，不得宣称低码率展示已经上线。
