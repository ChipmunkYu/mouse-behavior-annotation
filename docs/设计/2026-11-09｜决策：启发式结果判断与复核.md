### 3.1 状态复用

| Video.workflow_status + judgment_status | 含义/允许动作 |
|---|---|
| draft + pending | 待判断；可领取/释放；首次可安全预填已知类别/参与关系供人工核对，不新增原始建议面板；人工确认后保存可用，或标不可用 |

## 4. 四文件输入与项目类别契约

### 4.1 可接收的单事件结构

annotation 顶层必须是单对象；禁止 `events` 多事件数组、`Multiple_behavior_candidates` 容器及全视频导入包冒充单事件。`behavior`/`canonical_behavior`/participants/actor_id/target_id 等是原始建议，**不是项目类别 ID 或角色分配 authority**。

```json
{
  "behavior": "upstream_label",
  "mouse_ids": [12, 31],
  "participants": [],
  "confidence": "heuristic_candidate",
  "frame_range": {"start": 15, "end": 74},
  "time_range": {"start": 0.5, "end": 2.5}
}
```

示例 fps=30，clip 可为 90 帧，不能将事件误写为 0–89。时间派生为 `start/fps`、`(end+1)/fps`；索引为片段内 0-based。结构性边界须 `0 <= start < end < N`，与现有禁止单帧规则一致；坏边界不是未知类别，不可静默修好。

- metadata 至少有 `schema_version`、`clip.filename=clip.mp4/fps/width/height/frame_count`、`tracks.frame_origin=0/time_origin=0/coordinate_system=clip_pixels`、`pose.keypoint_names/skeleton_edges`；版本值不是兼容性充分条件。source/provenance 是证据，可带原视频绝对帧，但不得用它覆盖局部事件边界。
- 本版可导出来源契约须在导入时验证：`source.video_filename` 为非空展示名；播放范围可用上游扁平 `source.start_frame/end_frame/start_time/end_time` 或网站嵌套 `source.clip`，二者同时出现须一致。源帧闭区间 `[S,E]` 须满足 `E-S+1=N`，并显式满足与 clip fps 的一对一帧/时间映射；`source.crop_region` 只作原画面来源证据。缺失或重采样而无法证明一对一映射时，单项拒绝 `unsupported_source_mapping`，不能先通过后在导出时猜来源。输入若提供 source.annotation，还须与 `S + annotation.frame_range` 一致；未提供时可在已验证的一对一映射上机械派生。此为网站接入约束，不声称上游现有包已满足。
- tracks 是逐帧 JSON 数组 `[{frame,time,detections:[{track_id,box,keypoints,detection_confidence,class_id}]}]`，frame 必须完整连续 0…N-1；空 detections 可表示缺测。ID 为既有 `track_ids.py` 合法范围的非布尔整数，不根据 RFID、原视频或其他候选重编号。box/点坐标、置信度和类别按现有有效检测规则校验，拒绝 null/NaN/Infinity/坏 box/尺寸不符；不得通过补框、补点、裁剪/钳位坐标来“兼容”输入。
- 适配为既有 RawDetection 及 DetectionImport：frame→frame_index，time→time_sec，box 数组→既有 box 字典，keypoints 按输入 pose 名称与顺序保留；内部需要时生成受控 JSONL 和平铺 metadata 后走既有插入/摘要流程。保存原四文件，规范化文件另取本 batch 专属名，不覆写原文件。不得将数组文件仅改后缀交给 `_validate_tracks_jsonl`，也不得把嵌套 metadata 直接交给 `_validate_metadata_json`。
- MP4 实测帧数、尺寸、fps、duration 必须与 metadata/数组相符；复用现有 probe 容差与帧权威检查，失败报错。输入为已经切好的媒体；网站不调用外部启发式、不跑 SAM、不重新生成事件。
- 原始 roles 未知、`actor_id/target_id=-1` 等不构成角色 authority；保留原始证据，待人工选择。检测几何不合法与角色未知分开处理：前者拒绝单项，后者可导入。

### 4.2 类别/角色最小可实现规则

网站当前没有全局跨项目 category key。导入与 GET 的 **`selection` 初始仍为 null**；2026-11-15 用户授权仅在前端第一次成功加载 `draft + pending + selection=null` 时预填草稿，不改 API、数据库或响应类型。依据为 `D:/lab/行为识别/行为定义.md` 的专家 15 类及 `D:/lab/行为识别/规范与流程/2026-11-14｜调研：新行为定义跨模块差异.md` 第 3 节生产 Project 2 证据；本地测试配置不代表生产已接通。

- 类别仅匹配显式别名组：Locomotion/Moving/移动、Static/stationary/静止、Grooming/理毛、Rearing/climb_wall/站立攀爬/爬墙、Approach/接近、Together/一起、Chasing/chase/追逐、Attack/attack_review/攻击/攻击行为、Snout-head contact/nose_head_contact/nose_head/鼻头接触、Snout-rear contact/nose_tail_contact/nose_tail/鼻尾接触、Huddling/huddle/扎堆/扎堆行为、Social clustering/社会聚集、Dispersal/dispersal_review/群体分散、Group locomotion/群体同步运动、Isolation/孤立/孤立行为。大小写、空格、下划线及连字符作统一格式处理，不作模糊匹配。同名但不在别名组的自定义类别不猜配。
- `behavior` 与 `canonical_behavior` 若均非空，必须均已知且同义；未知、冲突或实时 `listCategories` 中有多个 active 匹配时不预填。类别 ID 一律取唯一匹配的本项目实时类别，不写死生产 ID，也不改类别名称或配置。
- `mouse_ids`、participants 的 `track_ids` 及 actor/target 仅收集当前 corrected tracks 中存在的非负安全整数，去重保留；`-1`、旧 merge ID、布尔值、字符串等无效。participants 逐项运行时窄化，未知结构不抛错、不猜测其他字段。
- 五类方向显式对应实际角色名：Approach 的 Approaching/Approached，Chasing 的 Chasing/Chased，Attack 的 Attacker/Attacked，鼻头接触的 Snout_contacting/Head_contacted，鼻尾接触的 Snout_contacting/Rear_contacted（并支持专家中文角色语义）。按实际 name 查找实时 key，或接受该类别实际 role_key；actor/target 仅表达该行为的主动/接受语义，不按角色定义数组位置或鼠 ID 大小分配。
- participants 的 role_key/role_name 同时给出时必须解析为同一个项目角色；同一角色不同来源的 ID 集合冲突、跨角色同鼠或超角色容量时，安全清空角色预填而保留合法参与鼠待分配。未知/缺角色不能用鼠 ID 顺序补齐，仍受现有完整角色与人数门禁约束。
- 已保存 `selection` 优先；前端预填不设 dirty，不自动 PUT、不标 usable、不提交。人工编辑后同步保留草稿，异步上下文刷新、409 刷新 CAS 及模式切换不覆盖编辑；终态以服务器结果只读为准。后续加载不会重新消费 input，身份修正后不能重放旧 ID；显式放弃修改恢复服务器 selection（无 selection 则清空），不是重新预填。

人工从 `GET /api/projects/{p}/categories` 的本项目 active 类别选择 `category_id`（项目类别方案须已锁定）。unordered 发送 mouse_ids，participant_roles 必须 `{}`；role_based 只发送完整项目 role-key→ID 数组，mouse_ids 禁传，由后端取并集。角色数量上下限、角色互斥、参与数、有效轨迹覆盖及社交行为连续性全部复用现有配置驱动门禁。缺角色、外部 role_key、跨项目类别、禁用类别及非法 ID 一律拒绝，不能因 heuristic 来源绕过。人工改类别时需完整重选/确认目标类别参与关系，不保留不兼容旧角色。

## 5. 上传、判断与复核 API JSON

路径中的 `p/v/b/s/a` 分别表示 project/video/batch/submission/snapshot ID；真实路径保留现有 `{project_id}` 等名称。除文件上传外均 JSON；新请求严格拒绝多余字段。HTTP 403 权限、404 项目内不存在、409 状态/CAS 冲突、422 结构错误；沿用现有业务校验的 400。新冲突用 `detail: {code,message,...}`，不返回服务器绝对路径。

### 5.1 复用 batch 协议，第四文件是新 role

`POST /api/projects/{p}/video-import-batches` 增加可选 body：省略或 `{ "source":"manual" }` 沿用旧客户端；heuristic 必须显式：

```json
{"source":"heuristic"}
```

201/GET batch 的既有字段保留，并新增：

```json
{"id":91,"source":"heuristic","status":"uploading","annotation_upload_state":"pending","created_video_id":null}
```

`PUT /api/projects/{p}/video-import-batches/{b}/files/{role}` 仍是 multipart `file`。heuristic 四 role 为 `tracks / metadata / annotation / video`，对应严格四文件名；manual 继续原三 role，不接受 annotation。所有完成检查、槽 CAS、取消清理、24 小时过期清理均须纳入第四槽，不能只修改允许 role 列表。

`POST .../{b}/complete?assignee_membership_id=...` 保留现有 query（不改成 JSON 负责人），heuristic 四槽缺一报 400，**不退化 video_only**。先完整校验并准备规范化检测，再同一事务创建 Video+DetectionImport+候选证据+batch ready，之后才调度展示代理。失败不公开半成品任务；重复 complete 返回同一结果。

```json
{"batch_id":91,"video_id":301,"created_video_id":301,"detection_import_id":81,"revision":1,"status":"ready","source":"heuristic","judgment_status":"pending","message":"候选已导入，等待人工判断"}
```

### 5.3 复核直接修改的快照事务

不能 PATCH SubmissionAnnotation，也不能先通过再 reopen 修改。submitted 时 `PUT judgment` 必须带当前非空 expected_submission_id/expected_decision_revision（其他 CAS 也必填），直接编辑后：

1. 验证当前唯一 submitted、输入不变、类别/角色与连续性全部合法，取得/校验原媒体身份。
2. 同一事务将旧 submitted 标为 withdrawn（保留旧快照/决定），更新唯一 live Annotation 和 annotation_revision。
3. 复用 `create_submission` 创建新 attempt 与不可变检测/行为快照；新 attempt 的 submitted_by 记录本次直接修改并重新生成快照的复核者，原判断者保留在 Annotation.annotator_id 和旧 attempt，不改作者伪造身份。返回新 submission_id/decision_revision。不得把旧 approved 单行为决定 carry 到新 heuristic attempt，需重新确认。
4. 全部成功才 commit；失败旧 submitted 保持原样。ReviewPage 刷新新快照后才能决定通过。这里不调用会自行 commit 的 HTTP withdraw/submit 路由串联。

merge/split 在 submitted 由 reviewer 发起时同样走这一事务收尾；新增 judgment 服务仅负责本功能流程，复用现有验证/快照函数，不搭通用工作流引擎。现有 `commit_split/commit_merge/undo_latest` 的 commit 上移至各调用路由，保证检测 delta、参与关系、withdraw/新 attempt 同成同败（suppress 调用点也需保持原事务行为）。

继续复用以下接口：

- `POST .../submit`：heuristic 必须 usable + 恰好一条合法 Annotation，再次完整校验；body 保留 `expected_submission_id/expected_decision_revision`，并扩展必填 heuristic 的 expected_annotation_revision/base_detection_import_revision/base_identity_revision。`create_submission` 必须禁止 heuristic 的跨尝试自动 carry。
- `PUT .../submissions/{s}/annotations/{a}/decision`：原 JSON `{status:"approved"|"rejected"|"pending",feedback,expected_decision_revision}`；rejected 必有反馈。单条 approved 仍未完成，pending 可回退。
- `POST .../review`：JSON `{"result":"approved","comment":null,"expected_submission_id":42,"expected_decision_revision":1}`；只能确认当前新快照。approved 原子完成并发布唯一 Clip；rejected 回到待修改，不发布 heuristic 资产。submitted heuristic 还可发送 `result:"unusable"`，沿用 can_review（允许自审）及完整 submission/decision CAS，原子记录 Submission.status/decided_at 和 Review 的审核人、时间、结论、submission_id，保留当前不可变快照，不要求伪造单行为 rejected；manual 对 unusable 返回 422。终态复用既有写锁，无 Clip/导出，不可 reopen/withdraw/edit。
- `POST .../withdraw`：heuristic 扩展必填 JSON `{"expected_submission_id":42,"expected_decision_revision":1}`；未完成才可撤回，所有决定随旧快照保留，下一次提交从 pending 开始。
- review-state 沿用既有结构，heuristic 完成时 `can_reopen=false`；reopen 路由本身必须 409 `heuristic_completed_locked`，不能仅 UI 隐藏。

## 6. 当前片段的 merge/split 与撤销

复用 `POST .../identity-edits/check`、`POST .../identity-edits`、`POST .../identity-edits/{edit_id}/revert`。scope 由 URL 的当前 Video/active import 决定；启发式一片段一 Video，不查找/传播至同源视频其他候选。

原 check/commit JSON 保留 `operation/track_ids/frame/base_identity_revision/base_detection_import_revision`，heuristic 的 check/commit/revert 额外要求 `expected_annotation_revision`，submitted 时再带 `expected_submission_id/expected_decision_revision`。check 响应扩展 `participant_confirmation_required` 与 `proposed_selection`（category_id、mouse_ids、participant_roles，或 null）；这些是预览，不授权写入。commit/revert 保留原返回字段，另返回最新 annotation_revision、selection、submission_id、decision_revision，前端据此刷新，不继续使用旧快照。

commit 可增加 `confirmed_selection`（与第 5.2 节 selection 请求同规则，只含类别和参与关系）。后端基于 CAS 版本重算预览；有歧义而未带确认时 409 `participant_confirmation_required`，**零写入**。确认不允许改变类别，仅显式指定该操作后的参与者/角色；类别变更走 judgment。split 的新 ID 由既有 next_display_track_id 预览/分配，版本变化即拒绝。

- merge：保留现有同帧多鼠冲突拒绝；同一角色内等价替换可去重，同一身份涉及多个角色不能随便保留一个角色。无法满足角色上下限或互斥时需明确的新合法选择，不能靠“确认”跳过校验。
- split：事件完全在切点前/后且可唯一投影时同步原/新 ID；跨切点、角色不明等情况要求确认，不能沿用现状“只标 needs_mouse_ids 却保存成可用”。pending 且无人工选择时只修正当前检测身份，仍保持 selection=null；usable 必须产生合法完整选择。
- 保存 before/after-image 到既有 DraftIdentityEdit.params，覆盖 unordered 与 role_based；检测 delta、参与者/角色、material evidence 和 annotation_revision 同事务。撤销严格 LIFO，并校验 after-image 未被后续人工改写，恢复 before-image、重新校验；冲突整次拒绝，不能覆盖用户后续判断。身份修订继续单调递增，不回拨。
- submitted 修改/撤销要有 reviewer 及当前快照 CAS，再按第 5.3 节换快照；draft/rejected 复用编辑权限。approved/unusable 禁止 check 以外所有身份写入；UI 同样只读。check 可以保留只读预览，但不显示可执行按钮。

## 7. 所有写入/撤回/reopen 旁路门禁

以下相对路径以 `/api/projects/{p}` 开始，`V=/videos/{v}`。终态限制在锁后判定，早期观察状态不能授权写；不能把 `allow_submitted=True` 解释成“允许完成后写”。批量接口全部或零写入。所有规则仅为 heuristic 增量，manual 原语义保留。

| 路由/写路径 | heuristic 门禁 |
|---|---|
| `POST V/annotations`、`PATCH/DELETE V/annotations/{id}` | 全状态拒绝 `heuristic_judgment_required`；只能专用 judgment 创建/改唯一 Annotation，不许旧 API 增删、改边界、置信度或 crop 绕过 |
| `PUT V/judgment`（新增） | 仅第 3/5 节可变状态；approved/unusable 409；submitted 仅 reviewer+完整 CAS |
| `POST V/identity-edits`、`.../{id}/revert` | 第 6 节角色同步、CAS、原子快照；完成后一律 409 |
| `POST V/detection-suppressions`、`.../{id}/revert` | heuristic 全状态拒绝：本功能只允许 merge/split，不提供检测抑制/删除能力 |
| `POST V/detection-imports`（替换检测） | heuristic 全状态拒绝；不能用替换检测、媒体元数据或新 baseline 绕过只改 ID 的范围 |
| `PUT/DELETE V/distance-calibration` | heuristic 拒绝；保留输入有效标尺，仅 manual 沿用该编辑能力 |
| `POST V/submit`、`POST V/withdraw` | 状态+内容+快照 CAS；usable 才 submit；withdraw 只当前 submitted，无最终 Review；不能让 unusable 重入任务 |
| `PUT V/submissions/{s}/annotations/{a}/decision` | 只当前未完成 attempt；approved/unusable 禁止 pending 回退及任意决定 |
| `PUT V/submissions/{s}/annotations/{a}/feedback-mark` | 未完成 rejected 反馈仍按既有权限；完成后禁止新写（已存在的幂等读取不改事实） |
| `POST V/review`、`POST V/submissions/{s}/reopen` | review 只当前 submitted；heuristic reopen 永远拒绝；review 终态后不得再次通过/退回 |
| `POST /videos/{v}/claim`、`/videos/claims`、`V/release`、`/videos/assignments` | 保留原角色、负责人和 draft/rejected 条件；完成/不可用排除且批量原子拒绝，不暗中重置状态 |
| `DELETE V` | heuristic 已成功导入的视频全状态拒绝，入口用不可用；只允许 batch 失败清理删除“本次尚未发布”产物，不借 hard-delete 删除成功数据 |
| `POST V/media/generate`、审核自动 enqueue、媒体 worker 和 export 自动 repair | 只对 final approved 的已发布 heuristic Clip 修复实体；不得为 draft/submitted/rejected/unusable 新建 Clip；修复仍只复制已切媒体，不重新切 |
| `GET V/annotations/export`、`GET V/detections/export` | heuristic 全状态拒绝 `heuristic_snapshot_export_required`，统一使用最终确认快照的项目导出；不能借旧 live JSON 导出旁路输出不可用/未确认数据。判断用 annotations/detections/corrected-tracks 的普通读取仍允许 |
| `POST /export` 与 worker frozen refs、`GET /clips`/categories/thumbnail、媒体读取 | 来源与 final 状态按第 8 节；不能借 legacy 分支或历史快照导出未确认 heuristic 结果 |

`video_write_gate.py` 为走 gate 的路由提供 heuristic 终态 guard；领取/改派直接 UPDATE、硬删除 service、导入 complete、后台发布/修复等各自补显式条件。第 5.3 节是唯一允许 reviewer 在 submitted 内改内容的专用路径，不对旧通用写接口统一放开 submitted。服务/触发器应防止 source、输入边界及完成后内容被内部函数误写；允许后台媒体任务更新 Clip 的实体状态，但不更新已确认语义。

- `POST /export` JSON 扩展为 `{"category_ids":[17],"source":"manual"}`，枚举 manual/heuristic/all，**省略默认 manual**。前端显式选“人工 / 启发式 / 全部”，默认人工；选全部才允许混合。`asset_rows`、export video gate、enqueue、冻结 payload/refs、worker 复核及 status 统计必须使用同一 source。
- `GET /export/status?source=manual|heuristic|all`、`GET /export/download?source=...` 也缺省 manual，不能下载“项目最近成功”但来源不同的 ZIP。来源范围与类别写入已有 job payload，旧 payload 无 source 解释为 manual；status/download 查匹配来源的任务，返回实际 source 与 category_ids，避免错误展示另一范围的结果。项目级 active export 排他仍复用，不增加来源队列。
- manual 的永久发布子集语义照旧；heuristic 只有 Video approved + usable、绑定最终 approved Submission 的唯一 Clip 可见/可导出。rejected/withdrawn/superseded heuristic 快照不能发布或混入 legacy。入队、worker 和发布前均复验，不能仅依赖 UI 来源过滤。

### 8.2 已切媒体在两个生成点都走复用分支

1. 最终 review approval 才创建 submission-bound Clip。`media_jobs.render_submission_clip_files` 根据不可变 Video.source 识别 heuristic，校验 staged source 身份、输入 SHA256、媒体参数和固定边界后，将**整个输入 MP4 原字节复制**到 `clips_dir` 的新临时名并原子发布，再生成缩略图；不调用 render_clip，不按 annotation 范围截取。不能直接把 videos_dir 路径塞入受 clips_dir 安全限制的 Clip.clip_path，也不使用共享可变硬链接。展示代理仍只是预览，不作为导出原件。
2. `export_jobs._write_item` heuristic 分支跳过 `_export_range` 的 padding、邻居规则及 render_clip。使用 `_ensure_clip` 得到的已验证原字节 Clip 复制为 `clip.mp4`；当前 `_build` 没有把该返回路径传入 `_write_item`，实现时须显式接通，不能只改 `_ensure_clip`。缺失资产修复也走上一条 copy 分支。
3. `_write_tracks_range` 按**整段 `[0,N-1]`**从最终 DetectionSnapshot 写 tracks，保留所有鼠及最终 display ID；输入已校验，crop=None，禁止再次空间裁剪/修补框点。输出 annotation 的类别、参与鼠、角色均从最终 SubmissionAnnotation，frame_range 仍为原事件局部区间、time_range 仍按 fps 派生，而不是全 clip。
4. metadata.clip 使用整段媒体 N/fps/尺寸，pose 从快照；source 采用第 4.1 节导入时验证的来源，统一输出 `source.video_filename`、`source.clip:{start_frame:S,end_frame:E,start_time,end_time}`、`source.annotation:{start_frame:S+s,end_frame:S+e,start_time,end_time}`、`source.crop_region`，其中 s/e 为不可变的局部事件边界，时间按已验证映射派生。不能将上传名 clip.mp4 伪作原始长视频名，也不能把局部边界和绝对帧混写。source.video_path、内部 ID/hash/路径及原 provenance 的非公开字段不带入训练四文件；缺少可验证映射的输入在导入阶段拒绝，不在导出阶段补猜。
5. 继续复用 `validate_clip_directory`（允许 annotation 是媒体子区间）、四文件集合检查、最终 ZIP CRC/快照身份检查、staging/原子发布/失败清理；不直接打包原 annotation.json/tracks.json，也不读取正在编辑的 live Annotation。通过后的类别、角色和 merge/split 必须反映在导出确认版本中。

## 9. 单项失败隔离与历史保护

heuristic complete 必须在公开 Video 前验证四文件及规范化产物；校验期间 batch=processing，无可领取 Video，也不调度代理。发布同一事务成功后 ready 是幂等事实；若 commit 结果不确定，使用既有独立会话确认思路核查 batch/Video/导入身份，不能因客户端断线误删已成功数据。

失败/取消清理扩展 `import_batch_cleanup.py / cleanup.py` 的四槽路径枚举、引用检查与过期处理，包含 annotation 原件和本次规范化文件。只允许删除该 batch 唯一拥有且未发布的随机路径，不能按 filename、event_id、source_video_filename 或 hash 全局删目录，也不“覆盖同名后回滚”。重试建新 batch，不重置旧 ready；同源/同名输入不隐含去重删除。

规范化 tracks/metadata 的存储名从本 batch 已持久化的随机原件 basename 派生固定 `.normalized.jsonl/.normalized.json` 后缀，临时写入用 `.part`；仅在 processing 内生成。这样进程中断后可由 batch 路径重新枚举本次产物，无需另造文件 manifest 表。成功时 DetectionImport 指向规范化文件，batch 保留原件路径，清理须同时检查两组引用；ready 批次不进入失败清理。

上传管理器捕获单项失败后执行受保护清理并继续调度其他队列项；全部终结后显示成功数、失败名/原因（同名附队列序号）。清理失败要保留明确“清理待重试”状态/提示并交给现有保守过期清理，不能假报已清理；若完整性无法确认则停止该项删除，其他项仍可处理。新批次不得留下半成品任务，旧 manual 路线已有的半成品清理保护不得放宽。
