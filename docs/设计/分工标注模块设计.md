## 1. 定位与权威边界

分工标注模块按完整视频记录当前负责人，提供成员管理、邀请码加入、单个/批量自领、释放、批量分配、筛选和数量统计。分工只表示责任归属，不构成编辑权限隔离：任一 active 项目成员均可标注、执行 track 修正和提交审核，行为标注继续记录真实 `Annotation.annotator_id`。

一个视频最多有一个当前负责人，也可以未分配。实现直接在 `Video` 保存负责人，不新增 `Task` 表、任务状态或分工历史；负责人变化不改写行为标注作者，不删除行为标注、审核数据、视频片段或共享 track 修正结果。

## 2. 角色与权限

项目角色固定为 `owner/admin/member`。审核能力独立表示为 `ProjectMembership.can_review`：

- owner、admin 始终可审核，不依赖字段值；member 仅在 `can_review=true` 时可审核。
- 任一 active 项目成员可编辑项目数据、单个或批量领取未分配草稿并提交审核；非负责人仍可编辑。
- owner/admin 可管理成员、邀请码、负责人和批量分配。
- 允许审核自己负责或参与标注的视频，不禁止自审。
- owner 不能被修改或移除；仍是当前负责人的成员不能被移除，须先改派或清空负责人。

`GET /api/projects` 同时返回当前用户的 `role`、`membership_id` 和有效 `can_review`，前端据此显示审核和管理入口。供普通成员选择或展示负责人的目录仅返回 `membership_id + username`，不暴露成员管理字段。

## 3. 成员与邀请码

每个项目保存一个唯一邀请码。owner/admin 可查看和重置；邀请码在重置前持续有效，重置后旧码立即失效。已登录用户通过邀请码加入时创建 `member + can_review=false` 的项目成员关系；重复加入幂等返回既有成员关系，并发唯一性竞争也收敛为同一关系。

成员管理支持将非 owner 成员设为 `admin/member`、设置 member 的 `can_review` 以及移除成员。owner/admin 的有效审核能力始终为 true。

## 4. 负责人和工作流规则

- 分配单位是完整视频；`Video.assignee_membership_id` 可空并引用同项目的 active `ProjectMembership`。
- 视频创建、单视频上传和三文件导入批次完成时可选负责人；只有 owner/admin 可指定，未指定即为未分配。
- 任一项目成员可把未分配且处于 `draft` 的视频单个或批量原子领取给自己的当前 membership；领取 CAS 同时校验项目、未分配与 `draft`。批量领取限定 1–200 个唯一 ID，全有或全无，任一无效或竞争统一返回 409，成功视频按请求顺序返回。
- 仅当前负责人可释放自己的视频，且视频必须为 `draft`；释放只清空负责人。
- owner/admin 可批量分配、改派或清空负责人，但目标视频必须全部属于该项目且处于 `draft/rejected`。
- 批量操作先验证全部目标并在单个事务内条件更新；任一目标冲突则整体回滚，不产生部分分配。
- 提交、通过和退回均保留负责人；`rejected` 默认由原负责人继续处理，owner/admin 也可改派。
- 分配变化不推进行为标注修订或媒体修订，也不创建后台任务。

视频库提供“我的任务 / 待领取 / 全部”三视图。“待领取”固定等于未分配 `draft`，不提供会放宽该口径的工作流筛选；“我的任务”和“全部”仍可叠加 `workflow_status`，owner/admin 可在“全部”按负责人筛选。owner/admin 在三个视图均可通过 checkbox、全选和桌面框选管理当前可见的可分配/改派视频；member 与 `member + can_review` 仅在“待领取”启用同类选择并批量自领，不获得负责人选择、改派或清空权限。粗指针或窄屏关闭框选但保留 checkbox 与全选。视频卡片仅“我的任务”显示“进入标注”，“待领取”只显示领取，“全部”无卡片主操作。项目管理页展示成员权限、邀请码、项目总统计和逐负责人统计；上传面板及三文件导入完成操作均支持可选负责人。

## 5. API

| 方法与路径 | 权限 | 语义 |
|---|---|---|
| `POST /api/projects/join` | 已登录用户 | 使用 `invite_code` 幂等加入项目 |
| `GET /api/projects/{project_id}/members` | owner/admin | 完整成员目录 |
| `GET /api/projects/{project_id}/assignees` | 项目成员 | active 负责人的精简目录 |
| `PATCH /api/projects/{project_id}/members/{membership_id}` | owner/admin | 更新非 owner 的 `role/can_review` |
| `DELETE /api/projects/{project_id}/members/{membership_id}` | owner/admin | 移除非 owner、且未负责视频的成员 |
| `GET /api/projects/{project_id}/invite` | owner/admin | 查看当前邀请码 |
| `POST /api/projects/{project_id}/invite/reset` | owner/admin | 重置邀请码 |
| `GET /api/projects/{project_id}/videos` | 项目成员 | `view=mine/unassigned/all`；`unassigned` 固定为未分配 `draft`，其余视图可筛 `workflow_status`，并支持相应负责人筛选 |
| `POST /api/projects/{project_id}/videos/{video_id}/claim` | 项目成员 | CAS 原子领取未分配 `draft`；负责人或状态冲突返回 409 |
| `POST /api/projects/{project_id}/videos/claims` | 项目成员 | 批量自领 1–200 个唯一视频 ID；全有或全无、统一 409，成功按请求顺序返回 |
| `POST /api/projects/{project_id}/videos/{video_id}/release` | 当前负责人 | 释放 `draft` 视频 |
| `POST /api/projects/{project_id}/videos/assignments` | owner/admin | 事务批量分配、改派或清空 |
| `GET /api/projects/{project_id}/assignment-stats` | 项目成员 | 项目及逐负责人的状态数量；同时返回 `unassigned` 与 `claimable` |

`POST .../videos` 的 JSON、`POST .../videos/upload` 的 multipart 和 `POST .../video-import-batches/{batch_id}/complete` 均接受可选 `assignee_membership_id`；非空时仅 owner/admin 可用，且目标必须是同项目 active 成员。`VideoOut` 返回 `assignee_membership_id` 和嵌套 `assignee`。

审核队列、裁决和审核相关媒体重试使用统一的有效审核权限：owner/admin 或 `member + can_review=true`。标注、track 修正和提交使用 active 成员权限，不再以旧 annotator/reviewer 角色隔离。

## 6. 数据迁移 0012

迁移 head 为 `0012`，从 `0011` 增量执行：

1. `projects.invite_code`：为存量项目生成不可空、唯一的邀请码。
2. `project_memberships.can_review`：不可空，默认 false；旧 `reviewer` 迁为 `member + can_review=true`，旧 `annotator` 迁为 `member + can_review=false`，owner/admin 保持角色。
3. 角色约束收敛为 `owner/admin/member`，保留 `project_id + user_id` 唯一，并增加 `(id, project_id)` 复合唯一约束。
4. `videos.assignee_membership_id`：可空；以 `(assignee_membership_id, project_id)` 复合外键引用成员 `(id, project_id)`，`ON DELETE RESTRICT`。存量视频保持 NULL，不推断负责人。
5. 为负责人列建立索引。downgrade 将可审核 member 映射回 reviewer、其他 member 映射回 annotator。

SQLite 额外安装三类 trigger，覆盖 ORM 和直接 SQL：视频插入/更新时负责人必须是同项目 active 成员；已负责视频的成员不得变为 inactive；外键阻止删除仍被引用的成员。Alembic 迁移和内存库 `create_all/ensure_schema` 共用同一 trigger 定义。

## 7. 并发与失败语义

- 单个与批量领取共用 `UPDATE ... WHERE assignee_membership_id IS NULL AND workflow_status = 'draft'` CAS 条件并固定写入当前 membership。单个接口保留既有错误契约；批量接口对缺失、跨项目、已分配或非草稿统一返回 409，更新数量不符时整体回滚。
- 批量分配去重视频 ID，并以项目、工作流状态条件一次更新；更新数量不符即回滚并返回 409。
- 创建、上传、导入完成、领取和批量分配都将 active/项目归属的数据库约束竞争转换为稳定 409；调用方可刷新后重试。
- 删除成员与并发分配竞争时，应用预检和数据库外键共同保证不会产生悬空负责人。
- 邀请码重置遇到唯一值碰撞会重新生成；邀请码加入依赖成员唯一约束保证幂等。

## 8. 统计口径

统计直接聚合 `Video.assignee_membership_id + workflow_status`，不落独立任务状态。项目总计返回 `total/draft/submitted/approved/rejected/unassigned/claimable`：`unassigned` 表示四种工作流状态中的全部未分配视频，`claimable` 表示未分配 `draft`，供“待领取”页签显示“可领取数”；两者不得混用。`by_assignee` 对每个项目成员返回负责总数及四种工作流状态数量。这里的“分配状态”仅指“已分配/未分配”，不得与视频工作流状态混用。

## 10. 保留的首版决策

首版保持完整视频单负责人，不拆分时间段，不增加任务状态机或分工历史；允许自审；`submitted/approved` 禁止管理员改派；负责人只表达责任归属而不限制编辑。这些决定如需改变，应同步修改本设计、需求文档、术语表和对应实现。
