# 视频加载参考方案

## 1. 参考方案链路


```text
Azure Blob Storage
  → 后端首次下载并缓存到 VM 本地磁盘
  → 浏览器通过 fetch 全量下载视频
  → 浏览器创建 Blob 对象
  → URL.createObjectURL(blob) 生成临时 blob: URL
  → <video> 从浏览器管理的数据中播放
```

完整下载后，播放、倍速和 seek 不再请求服务器；切换视频时终止旧下载并释放旧 Blob URL。


### 数据规格

参考项目的视频单文件 55–73 MB。

为 1920×368、30 fps、H.264，单文件 55–73 MB。在约 0.7 MB/s 的低带宽下，首次下载约需 79–104 秒。

### 所用关键技术

**文件传输方式**，在本项目中应当指的就是 HTTP range 浏览器按需部分加载 or 前端 fetch 完整视频 → res.blob() 二选一。

| 技术 | 作用 |
|---|---|
| Azure Blob Storage | 持久保存视频对象。 |
| Managed Identity、`DefaultAzureCredential` | 让后端访问 Azure，无需在源码中保存账户密钥。 |
| `azure-storage-blob` | 后端下载 Azure Blob。 |
| 后端本地磁盘缓存 | 首次下载后复用 VM 本地文件，避免重复访问 Azure。 |
| FastAPI 同步 `def` 路由 | 将同步 Azure SDK 调用放入线程池，避免阻塞异步事件循环。 |
| Fetch 全量下载 | 浏览器下载完整视频，并可按已接收字节显示进度。 |
| 浏览器 Blob | 保存已下载的视频字节；具体由浏览器管理在内存或临时磁盘中。 |
| `URL.createObjectURL()` | 为 Blob 创建当前浏览器会话内可供 `<video>` 使用的临时地址。 |
| `AbortController` | 切换视频时立即终止旧请求。 |
| `URL.revokeObjectURL()` | 解除 Blob URL 映射，使浏览器可回收相关资源。 |
| FFmpeg `-movflags +faststart` | 将 MP4 的 `moov atom` 移到文件头，便于 Web 播放器尽早读取索引。 |
| 密集关键帧 | 缩短 seek 时从关键帧解码到目标帧的距离；参考视频为 30 fps、每 15 帧一个关键帧。 |


至于发送文件的其他流程，对加载速度影响可以忽略，简要罗列如下：
### 文件传输全流程

HTTP Range 与 Fetch Blob 的整体链路相近，差异主要集中在“浏览器如何取得视频字节”：Range 按需取部分数据，Fetch Blob 必须取完整文件。对小文件差别可能不明显，但对数百 MB 至 GB 级视频，首次等待、内存占用和 seek 时的网络行为差异很大。

1. **文件准备**：视频存于 Azure Blob Storage 或服务器磁盘，必要时由 FFmpeg 生成低码率 H.264 MP4，并用 `-movflags +faststart` 将 `moov atom` 移到文件头。
2. **发起播放**：前端向 FastAPI 请求视频或短期 stream ticket，并用 `AbortController` 管理请求生命周期。切换视频时立即 abort 旧请求，避免旧传输继续占用网络。
3. **认证与选源**：FastAPI 校验登录和项目权限，再选择原视频或低码率代理；访问 Azure 时可通过 Managed Identity、`DefaultAzureCredential` 和 `azure-storage-blob` 获取文件。后端本地磁盘缓存可避免同一视频反复从 Azure 下载。
4. **服务器发送**：当前可由 FastAPI `FileResponse`/`StreamingResponse` 返回字节，也可在鉴权后通过 `X-Accel-Redirect` 交给 Nginx。Nginx 可用 `sendfile` 高效读取磁盘，并处理 `Range` 请求，降低 Python 进程的传输负担。
5. **Range 路径**：浏览器以 `<video src>` 发出 `Range: bytes=...`，服务器返回 `206 Partial Content`、`Content-Range` 和对应字节。浏览器边取边播，seek 时按新位置再次请求局部范围，不等待完整文件。
6. **Fetch Blob 路径**：前端用 Fetch API 下载完整响应，经 `response.blob()` 创建浏览器 Blob，再用 `URL.createObjectURL()` 生成临时 `blob:` URL 交给 `<video>`。下载完成后播放和 seek 从浏览器管理的数据读取，不再访问服务器。
7. **解码与叠加**：HTML5 `<video>` 解码 H.264 并显示画面，检测框 JSON 可并行加载，再由 Canvas 或 SVG 叠加。密集关键帧可缩短 seek 后从关键帧解码到目标帧的距离。
8. **释放资源**：Range 路径需停止 `<video>` 并取消在途请求；Blob 路径还需调用 `URL.revokeObjectURL()`。两者都应阻止旧请求和旧事件污染新视频状态。



## 2. 本项目原视频大小

秋采数据样本按总码率推算，20 分钟约 2.668 GB。

详细信息：`WIN_20260822_18_53_17_Pro_part001.mp4` 的 `ffprobe` 实测为：H.264 Main、1920×1080、约 30 fps、无音频，视频流约 17.786 Mbps，容器总码率约 17.789 Mbps。其时长约 17 分 36 秒，文件大小约 2.348 GB；


预计低码率代理20 分钟约 600 MB。

详细信息：暂定规格为固定 1280×720、H.264/`libx264`、CRF 28、`veryfast`、`yuv420p`、无音频并开启 faststart；固定 GOP 30 帧，使用 `-g 30 -keyint_min 30 -sc_threshold 0` 关闭 scene cut 额外关键帧。按项目视频 30 fps 计算，每 1 秒一个关键帧；参数仍须经 P0 实测锁定。按 4 Mbps 估算，文件约为上述实测原片推算值的 22.5%；CRF 属于质量模式，实际大小会随画面复杂度变化。

## 3. 网速与全量下载等待时间

| 实际下载速度 | 实测原片推算：20 分钟约 2.668 GB | 代理候选估算：20 分钟约 600 MB |
|---:|---:|---:|
| 0.7 MB/s | 约 1 小时 3 分 32 秒 | 约 14 分 17 秒 |
| 1 MB/s | 约 44 分 28 秒 | 约 10 分钟 |
| 5 MB/s | 约 8 分 54 秒 | 约 2 分钟 |
| 10 MB/s | 约 4 分 27 秒 | 约 1 分钟 |
| 12.5 MB/s（100 Mbps 理论上限） | 约 3 分 33 秒 | 约 48 秒 |
| 125 MB/s（1 Gbps 理论上限） | 约 21.3 秒 | 约 4.8 秒 |

未计入协议开销、网络波动、服务器并发、浏览器处理和磁盘读写；实际时间通常更长。

## 4. 视频以外的信息加载相较而言可忽略

应区分三个过程：

1. **检测框数据加载**：通常是较小的 JSON，可与视频下载并行。
2. **检测框绘制**：Canvas 或 SVG 绘制已有结果，通常为毫秒级，但必须等视频已有可显示帧。
3. **模型推理**：若检测框尚未生成，则属于独立计算任务，耗时取决于视频时长、模型和硬件，不能与前端绘制等同。

在“全量下载后创建 Blob URL”的方案中，即使检测框 JSON 已提前加载，画面和叠加框仍需等待完整视频下载。若检测结果已存在，主要耗时通常是约 2.668 GB 原片或约 600 MB 代理的网络传输，而不是前端绘框。

## 5. 方案比较与当前决策

以下统一采用当前实测原片约 17.79 Mbps、低码率代理候选 4 Mbps 估算。等待时间只计算数据传输，不含鉴权、网络往返、浏览器处理和解码，实际通常更长。

> **当前决策：采用方案1“一次性加载 + 低码率”。** 四个展示入口完整下载低码率代理，经 `response.blob()` 和 `URL.createObjectURL()` 创建本地播放源；原视频继续作为片段生成、Submission 冻结和导出的唯一权威源。

> **人工清晰度确认（2026-08-28）：** 秋采数据9鼠样本的约10秒代理采用 1280×720、H.264/libx264、CRF 28、`veryfast`、30帧GOP和无音频配置；用户确认降码率后仍可用人眼识别小鼠。该记录只确认当前候选的主观画质，不代表完整 P0、网站接入或生产部署已经完成。

### 5.1 一次性加载 + 低码率

保留 20 分钟时长，先生成约 1280×720、4 Mbps 的低码率代理。浏览器完整下载约 600 MB 后创建 Blob URL；之后逐帧、倍速和 seek 基本不再依赖网络。

| 实际下载速度 | 20 分钟代理约 600 MB 的等待时间 |
|---:|---:|
| 0.7 MB/s | 约 14 分 17 秒 |
| 1 MB/s | 约 10 分钟 |
| 5 MB/s | 约 2 分钟 |
| 10 MB/s | 约 1 分钟 |
| 12.5 MB/s（100 Mbps 理论上限） | 约 48 秒 |
| 125 MB/s（1 Gbps 理论上限） | 约 4.8 秒 |

若要求 20 秒内完整加载，600 MB 至少需要 30 MB/s，即约 240 Mbps 的实际吞吐。因此，4 Mbps 已明显小于原片，但在普通公网和低带宽下仍不能解决首次等待。

### 5.2 一次性加载 + 原画质 + 3–5 分钟独立文件

数据生产端不再输出约 20 分钟文件，而是直接输出 3–5 分钟原画质独立文件；网站不做中间切分。现有实测样本中，3 分钟约 401 MB，5 分钟约 668 MB。浏览器仍需完整下载后创建 Blob URL。

| 实际下载速度 | 3 分钟原片约 401 MB | 5 分钟原片约 668 MB |
|---:|---:|---:|
| 0.7 MB/s | 约 9 分 33 秒 | 约 15 分 54 秒 |
| 1 MB/s | 约 6 分 41 秒 | 约 11 分 8 秒 |
| 5 MB/s | 约 1 分 20 秒 | 约 2 分 14 秒 |
| 10 MB/s | 约 40 秒 | 约 1 分 7 秒 |
| 12.5 MB/s（100 Mbps 理论上限） | 约 32 秒 | 约 53 秒 |
| 125 MB/s（1 Gbps 理论上限） | 约 3.2 秒 | 约 5.3 秒 |

若要求 20 秒内完整加载，3 分钟文件至少需要约 20.1 MB/s（161 Mbps）。

该方案的优势是保持原画质、下载完成后操作稳定，且网站无需维护切片逻辑；代价是低带宽等待仍长，文件和任务数量增加。

### 5.3 HTTP Range 分批加载 + 较低码率

仍使用约 4 Mbps 的 20 分钟代理，但浏览器不等待完整 600 MB，而是通过 HTTP Range 按播放位置请求局部字节。

为给出可比量级，假设首次取得约 5 秒视频内容：4 Mbps × 5 秒约为 2.5 MB。实际首批请求量由 MP4 索引、关键帧、浏览器缓冲策略和起播位置决定。

| 实际下载速度 | 首批约 2.5 MB 的纯传输时间 |
|---:|---:|
| 0.7 MB/s | 约 3.6 秒 |
| 1 MB/s | 约 2.5 秒 |
| 5 MB/s | 约 0.5 秒 |
| 10 MB/s | 约 0.25 秒 |
| 12.5 MB/s（100 Mbps 理论上限） | 约 0.2 秒 |
| 125 MB/s（1 Gbps 理论上限） | 小于 0.1 秒 |

上表不是首帧承诺；还需叠加鉴权、票据、网络往返、MP4 索引读取和浏览器解码。4 Mbps 代理在 1 倍速下持续需要约 0.5 MB/s，0.7 MB/s 网络理论可播放但余量较小。seek 会触发新的 Range 请求，响应速度还受网络延迟和关键帧位置影响。

### 5.4 方案对比

| 方案 | 0.7 MB/s 示例 | 5 MB/s 示例 | 下载后的体验 | 主要限制 |
|---|---:|---:|---|---|
| 一次性 + 20 分钟低码率 | 约 14 分 17 秒 | 约 2 分钟 | 完全本地化，seek 稳定 | 600 MB 仍偏大 |
| 一次性 + 3–5 分钟原画质 | 约 9 分 33 秒至 15 分 54 秒 | 约 1 分 20 秒至 2 分 14 秒 | 原画质、完全本地化 | 低带宽等待长，文件数增加 |
| Range + 20 分钟较低码率 | 首批纯传输约 3.6 秒 | 首批纯传输约 0.5 秒 | 可快速开始播放 | 持续播放和 seek 仍依赖网络 |

若首要目标是多数网络下尽快开始播放，方案三的首次等待更短；但当前更重视完整下载后的逐帧、倍速与 seek 稳定性，以及四入口实现一致，因此决定采用方案一。该决策接受约 600 MB 代理在低带宽下首次等待较长的限制，实施前仍须通过 P0 实测确认代理大小、浏览器 Blob 资源占用和目标网络下的可接受性。
