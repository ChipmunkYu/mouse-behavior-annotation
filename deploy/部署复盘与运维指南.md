# 部署复盘与运维指南

> 适用对象：第一次独立部署 FastAPI + React + SQLite + Nginx 的维护者。
>
> 文档性质：本次部署的真实复盘，以及下一次可直接执行的标准操作流程（SOP）。
>
> 事实基线：仓库当前 `integration/spatial-final` 分支、`deploy/README.md`、部署配置和仓库外 `网站服务器文件清单.md`。服务器实时状态发生变化时，以重新核验结果和服务器清单为准。
>
> 安全约束：本文不记录生产登录账号、密码、`SECRET_KEY`、token、私钥内容或邮箱。所有生产凭据均使用占位符表示。

## 1. 总览：系统如何工作

### 1.1 请求链

```text
浏览器
  |
  | HTTP :80 / HTTPS :443
  v
Nginx
  |-- /、静态资源 ----------------------> React/Vite 构建产物（SPA）
  |                                      /opt/mouse-annotation/current/frontend/dist
  |
  |-- /api/health、/api/auth/login ------> FastAPI 127.0.0.1:8000
  |
  `-- 其他 /api、上传路由
         |
         | auth_request /_auth
         | internal /_auth -> /api/auth/me
         | 鉴权通过后才转发原请求
         v
      FastAPI 127.0.0.1:8000（单进程 Uvicorn）
         |-- SQLite ----> /data/mouse-annotation/data/annotation.db
         |-- 媒体数据 --> /data/mouse-annotation/data/
         |-- 临时文件 --> /data/mouse-annotation/tmp（TMPDIR）
         `-- FFmpeg/ffprobe --> 视频探测、缩略图、片段生成等
```

### 1.2 发布与运行时结构

```text
/opt/mouse-annotation/releases/<COMMIT>/   不可变 release：代码、前端 dist、后端 .venv
                    ^
                    |
/opt/mouse-annotation/current ------------+ 原子软链接，决定当前应用版本

/etc/systemd/system/mouse-annotation.service
  |-- WorkingDirectory=/opt/mouse-annotation/current/backend
  |-- EnvironmentFile=/home/jinghan/.config/mouse-annotation/backend.env
  |-- TMPDIR=/data/mouse-annotation/tmp
  |-- UMask=0027
  `-- Uvicorn 127.0.0.1:8000 --workers 1

/etc/nginx/sites-enabled/mouse-annotation.conf
  `-- 静态站点、TLS、auth_request、API 与上传反向代理
```

这套结构有四个关键点：代码 release 可以替换，`backend.env` 长期稳定，数据库和媒体不随发布移动，`current` 只在新版本完成构建、依赖安装和迁移后切换。SQLite、应用内任务执行器和运行时数据目录目前按单进程设计，不应擅自增加 Uvicorn worker 数量。

## 3. 分支与提交演进

本次部署来源分支为 `integration/spatial-final`，不是 `main`。四个关键提交按时间演进如下：

| 短提交 | 作用 | 部署意义 |
|---|---|---|
| `0d05e1c` | 初始生产部署配置 | 建立固定 release、生产 env 模板、systemd、Nginx 和同源 `/api` 基线 |
| `f6f0077` | `UMask=0027` 权限加固 | 防止 SQLite sidecar、媒体和日志默认成为 `0644` 等宽权限文件 |
| `c9b0ba6` | HTTPS 上传入口加固 | 增加 TLS、上传路由、20 GiB 特例、连接限制、超时、`TMPDIR` 和前置鉴权；`/_auth` 已关闭请求 body 并清空 `Content-Length` |
| `0b44ace` | `/_auth` 大请求热修 | 仅补充 `client_max_body_size 0`，避免子请求 location 对继承自原请求的大 `Content-Length` 应用默认 1 MiB 限制 |

当前存在需要明确管理的“来源不完全一致”：

- `/opt/mouse-annotation/current` 当前应用 release 是完整提交 `c9b0ba6...`。
- 运行时 Nginx 配置已单独安装提交 `0b44ace` 的 `/_auth` 热修。
- 因此线上行为包含 `0b44ace`，但 `current` 本身没有指向一个完整的 `0b44ace` release。
- 下次正式发版应按本文 SOP 为 `0b44ace` 或其后继固定提交创建完整 release、构建和验收，再原子切换 `current`，恢复代码、部署模板和线上配置来自同一提交的可追溯性。

## 5. 从零部署 SOP

### 5.1 执行规则和占位符

以下命令是模板，不代表需要在阅读本文时执行。**任何服务器命令，包括只读命令，实际执行前都应先确认目标服务器、逐条展示命令、说明目的并获得明确确认。所有含 `sudo` 的命令都由用户在自己的终端执行并自行输入 sudo 密码；不要把密码拼入命令、脚本、聊天或日志。**

常用占位符：

```text
<SSH_USER>               服务器 SSH 用户
<SSH_KEY_PATH>           本机 SSH 私钥路径
<REPO_SSH_URL>           私有仓库 SSH URL
<COMMIT>                 完整 40 位目标提交哈希
<PRODUCTION_USERNAME>    生产应用用户名，仅在交互输入时提供
<DOMAIN>                 正式域名，例如已批准的生产域名
<CERT_SOURCE_PATH>       管理员提供的 PEM 证书链本地/暂存路径
<KEY_SOURCE_PATH>        与证书匹配的私钥本地/暂存路径
```

每一步都遵循“目的 → 命令模板 → 成功证据 → 失败停止点”。任一步不满足成功证据，都不要继续切换 `current`、restart 或对公网开放。

除第 14、15 步明确标为“本地 PowerShell”外，本节所有 `bash` / `python` 代码块都在**目标 Ubuntu 服务器的交互式 Bash** 中运行。不要把多行模板嵌进本地 PowerShell 的双引号 `ssh "..."` 参数；否则 `$HOME`、`$uri`、`$timestamp` 等可能先被本地展开。需要远程自动化时，应传输并审阅脚本，或使用能阻止本地插值的可靠引用方式。

### 第 1 步：只读盘点

目的：确认登录的是目标网站服务器，核对系统、磁盘、工具和监听端口，防止把命令运行到其他服务器。

```bash
hostnamectl

nproc
free -h
df -hT / /data
python3 --version
sqlite3 --version
ffmpeg -version
ffprobe -version
nginx -v
git --version

```

成功证据：Ubuntu 22.04、4 CPU、约 14 GiB 内存、`/` 约 47G、`/data` 约 126G；版本与第 2 节一致；8000 未对公网监听。

失败停止点：主机、磁盘挂载、容量或用途不匹配；`/data` 未挂载；发现未知进程占用 80/443/8000；不得继续。

### 第 2 步：使用只读 Deploy Key 获取固定提交

目的：从私有仓库建立不可变 release，不依赖开发机工作区，也不使用可写个人 token。

```bash
test ! -e "/opt/mouse-annotation/releases/<COMMIT>"
install -d -m 0755 "/opt/mouse-annotation/releases"
GIT_SSH_COMMAND='ssh -i /home/jinghan/.config/mouse-annotation/ssh/github_deploy_ed25519 -o UserKnownHostsFile=/home/jinghan/.config/mouse-annotation/ssh/known_hosts -o IdentitiesOnly=yes' git clone --no-checkout "<REPO_SSH_URL>" "/opt/mouse-annotation/releases/<COMMIT>"
git -C "/opt/mouse-annotation/releases/<COMMIT>" checkout --detach "<COMMIT>"
git -C "/opt/mouse-annotation/releases/<COMMIT>" rev-parse HEAD
git -C "/opt/mouse-annotation/releases/<COMMIT>" status --short
```

成功证据：`rev-parse HEAD` 与完整 `<COMMIT>` 完全相同，`status --short` 无输出，Deploy Key 在仓库侧只读。

失败停止点：目标目录已经存在、主机指纹不明、提交哈希不一致、工作区有修改、Deploy Key 具有不必要写权限。不要用 `git pull` 修补旧 release，应删除未投入使用且确认无用的失败目录后重新创建。

### 第 3 步：创建 venv 并安装后端依赖

目的：将 Python 依赖隔离在本 release 内，不污染系统 Python。

```bash
python3 -m venv "/opt/mouse-annotation/releases/<COMMIT>/backend/.venv"
"/opt/mouse-annotation/releases/<COMMIT>/backend/.venv/bin/python" -m pip install --timeout 120 --retries 10 -r "/opt/mouse-annotation/releases/<COMMIT>/backend/requirements.txt"

```

成功证据：依赖安装退出码为 0，`pip check` 输出无破损依赖。

失败停止点：磁盘不足、编译失败或多次下载失败。网络抖动可以增加超时和重试后重新执行，但不要改用系统级 `sudo pip`。

### 第 4 步：显式加载 NVM PATH 并构建前端

目的：在非交互 SSH/脚本环境中使用已安装的 Node 22 和 npm 10，并通过锁文件构建确定性产物。

```bash
export NVM_DIR="$HOME/.nvm"
[ -s "$NVM_DIR/nvm.sh" ] && . "$NVM_DIR/nvm.sh"
nvm use 22
node --version
npm --version
cd "/opt/mouse-annotation/releases/<COMMIT>/frontend"

```

成功证据：Node 22、npm 10；`npm ci` 和 `npm run build` 成功；`dist/index.html` 存在。

失败停止点：`node` 不存在、npm 生命周期脚本报找不到 `sh`、锁文件不一致、构建失败或 `.env.production` 的 API 基址不是同源 `/api`。不要把本地 Windows PATH 展开后传给服务器。

### 第 5 步：安全生成稳定 `backend.env`

目的：把生产配置与 release 分离，以 `0600` 原子写入稳定路径。以下脚本只在服务器终端交互读取生产用户名和密码，不回显密码，不把 secret 写入命令历史。

```bash
install -d -m 0700 "/home/jinghan/.config/mouse-annotation"
umask 0077
python3 - <<'PY'
import getpass
import json
import os
import secrets
import tempfile
from pathlib import Path

target = Path("/home/jinghan/.config/mouse-annotation/backend.env")
username = input("Production username: ").strip()
password = getpass.getpass("Production password: ")
if not username or "\n" in username or "\r" in username:
    raise SystemExit("拒绝写入：用户名不能为空或包含换行")
if ("\n" in password or "\r" in password or len(password) < 12
        or password in {"demo123", "CHANGE_ME"}):
    raise SystemExit("拒绝写入：密码不得含换行、不得少于 12 字符或使用占位值")
values = {
    "ENV": "production",
    "DATA_DIR": "/data/mouse-annotation/data",
    "SECRET_KEY": secrets.token_urlsafe(48),
    "DEMO_USERNAME": username,
    "DEMO_PASSWORD": password,
    "CORS_ORIGINS": "https://<DOMAIN>",
    "FFMPEG_PATH": "ffmpeg",
    "FFPROBE_PATH": "ffprobe",
    "MEDIA_SYNCHRONOUS": "false",
}
# JSON 双引号和转义是 python-dotenv 可解析的 dotenv 值格式。
content = "".join(
    f"{key}={json.dumps(value, ensure_ascii=False)}\n" for key, value in values.items()
)
fd, temporary = tempfile.mkstemp(prefix=f".{target.name}.", dir=target.parent)
try:
    os.fchmod(fd, 0o600)
    with os.fdopen(fd, "w", encoding="utf-8") as stream:
        fd = -1
        stream.write(content)
        stream.flush()
        os.fsync(stream.fileno())
    os.replace(temporary, target)
    os.chmod(target, 0o600)
except BaseException:
    if fd >= 0:
        os.close(fd)
    try:
        os.unlink(temporary)
    except FileNotFoundError:
        pass
    raise
print(f"已安全写入 {target}；未输出凭据内容")
PY
stat -c '%U:%G %a %n' "/home/jinghan/.config/mouse-annotation/backend.env"
```

执行前必须把脚本中的 `<DOMAIN>` 替换为正式域名；生产应用用户名对应 `<PRODUCTION_USERNAME>`，只能在提示符内输入，不能直接写进文档或 shell 命令。

成功证据：文件路径稳定、所有者是服务用户、权限严格为 `600`；应用配置加载成功且不输出配置内容。所有 dotenv 值均经过 `json.dumps` 安全引用，密码可包含空格和标点；迁移由 Python 在进程内解析，不由 shell 执行 env 内容。

失败停止点：文件权限不是 `0600`、存在 `CHANGE_ME`、仍使用开发账号、密码少于 12 字符、`SECRET_KEY` 少于 32 字符、生产 CORS 不正确。生产配置会 fail-fast，应修正配置而不是绕过校验。

### 第 7 步：用真实 FFmpeg 验收 25/30/60 FPS

目的：用项目的 `build_submission_media_plan` 将双端 inclusive 帧范围转换成半开时间区间，再由项目的 `FfmpegMediaProcessor` 真实生成片段和缩略图；不能先生成期望帧数的成品再用 `ffprobe` 自证。

```bash
cd "/opt/mouse-annotation/releases/<COMMIT>/backend"
./.venv/bin/python - <<'PY'
import json
import shutil
import subprocess
import tempfile
from pathlib import Path

from app.media import FfmpegMediaProcessor
from app.submission_media_plan import build_submission_media_plan

root = Path(tempfile.mkdtemp(prefix="fps-acceptance-", dir="/data/mouse-annotation/tmp"))
processor = FfmpegMediaProcessor(ffmpeg_path="ffmpeg", ffprobe_path="ffprobe")
cases = [
    (25, 25, 75, {"x": 0, "y": 0, "w": 320, "h": 240}, 51),
    (30, 30, 90, {"x": 20, "y": 20, "w": 240, "h": 180}, 61),
    (60, 60, 120, {"x": 40, "y": 40, "w": 160, "h": 120}, 61),
]

def run(args):
    return subprocess.run(args, check=True, capture_output=True, text=True)

def assert_frame_decodes(path, index):
    result = run(["ffmpeg", "-v", "error", "-i", str(path),
                  "-vf", f"select=eq(n\\,{index})", "-frames:v", "1",
                  "-f", "framemd5", "-"])
    assert len([line for line in result.stdout.splitlines()
                if line and not line.startswith("#")]) == 1

try:
    for fps, start_frame, end_frame, crop, expected_frames in cases:
        source = root / f"source-{fps}.mp4"
        clip = root / f"clip-{fps}.mp4"
        thumbnail = root / f"thumbnail-{fps}.jpg"
        run(["ffmpeg", "-v", "error", "-y", "-f", "lavfi", "-i",

             "-pix_fmt", "yuv420p", str(source)])
        plan = build_submission_media_plan(
            start_time=start_frame / fps,
            end_time=(end_frame + 1) / fps,
            start_frame=start_frame,
            end_frame=end_frame,

            frame_count=5 * fps,
            width=640,
            height=480,
            crop_region=crop,

PY
```

脚本以 5 秒测试源作为输入，不预制期望长度的输出；实际片段完全由项目计划与处理器生成。验收基线分别是：51 帧、320x240、2.04 秒；61 帧、240x180、约 2.034 秒；61 帧、160x120、约 1.017 秒。每例还必须得到 crop 后同尺寸且可解码的 JPEG 缩略图，片段首帧和末帧均可单独解码；无论成功或失败，`finally` 都清理一次性输入和产物。

成功证据：`ffprobe` 的帧数、尺寸、帧率和时长符合基线，应用真实媒体流程成功。

失败停止点：编码器不可用、帧数或时长明显不符、应用只在 Fake processor 测试中通过。不得把“自动化测试通过”替代真实 FFmpeg 验收。

## 6. 故障复盘表

| 现象 | 根因 | 本次修复 | 下次预防 |
|---|---|---|---|
| PowerShell 发出的 SSH 命令里 `$变量` 消失、引号错位 | 本地 PowerShell 先展开双引号内容，再把结果传给远端 shell | 改用可靠的单引号/转义，复杂脚本减少跨两层 shell 的插值 | 分清“本地 PowerShell 解析”和“远端 Bash 解析”；实际执行前显示最终命令；复杂内容优先落为受审脚本 |
| NVM 已安装，但非交互 SSH 中 `node: command not found` | NVM 只在交互 shell 初始化，非交互命令没有加载 `nvm.sh` | 显式设置 `NVM_DIR` 并 source `nvm.sh` | 每次构建先输出 `node --version`、`npm --version`，不要假设 profile 已加载 |
| npm 生命周期脚本报找不到 `sh` | PATH 在本地被展开或传输时被破坏，远端系统目录不在 PATH | 在远端 shell 内加载 NVM，保留远端自身 PATH | 不从 Windows 拼装 Linux PATH；将完整构建命令置于远端单引号或经审核脚本中 |
| pip 下载超时 | 网络抖动或默认 read timeout 太短 | 使用 `--timeout 120 --retries 10` 重试，最终安装成功并通过 `pip check` | release 构建预留重试时间；失败后保持 release 未切换；不使用系统级 pip |
| `annotation.db` 为 `0644`，新 sidecar 可能继续宽权限 | 首次迁移时 umask 太宽；服务未设置 `UMask` | 数据库收紧为 `0640`，systemd 增加 `UMask=0027`，迁移前执行 `umask 0027` | 将权限检查作为迁移和上线验收项，检查 `-wal`、`-shm`、media 和 log |
| 生产启动在访问数据库前退出 | env 仍含模板占位凭据或开发默认值 | 保留 fail-fast，安全生成真实生产值 | 不复制模板为成品；切换前用同一 `Settings` 路径执行迁移/检查；绝不绕过校验 |
| Nginx 已关闭请求缓冲，上传仍会使用临时盘 | `proxy_request_buffering off` 只控制 Nginx；FastAPI/Starlette `UploadFile` 会先解析 multipart，超过 1 MiB 的内容 spool 到 `/tmp` | systemd 设置 `TMPDIR=/data/mouse-annotation/tmp`，并用 `ExecStartPre` 确保目录存在 | 容量规划同时覆盖最终媒体和临时 spool；不要误称为网络直写最终文件 |
| 大上传先经过鉴权，应用还没处理文件就失败 | `auth_request` 在原上传请求前调用 `/_auth` | 保留前置鉴权，但让子请求不携带 body | 上传入口验收必须同时观察主请求和鉴权子请求日志 |
| 大文件上传时 `/_auth` 触发 1 MiB 413，外部表现为 500 | 鉴权子请求 location 仍会对继承自原请求的大 `Content-Length` 应用默认 1 MiB 限制 | `c9b0ba6` 已关闭子请求 body 并清空 `Content-Length`；`0b44ace` 仅补 `client_max_body_size 0`，阻止 location 在子请求阶段拒绝大长度 | 为部署配置保留回归测试；完整 release 必须包含 `0b44ace`；遇到外部 500 先查 Nginx error log 的子请求状态 |
| 管理员给了多个证书包，不确定使用哪个 | Apache 与 Nginx 包的文件组织不同；Nginx 需要 PEM 证书链和匹配 key | 使用 Nginx PEM 包，安装前检查 SAN、chain、有效期和 key match | 明确索取 Nginx PEM chain + key；不把单张叶证书误当完整链 |
| 服务器装有 Certbot，但证书不是 Certbot 签发 | 本次使用管理员提供的 DigiCert 证书，Certbot 安装状态不等于证书来源 | 按人工证书路径安装，不创建虚假的 Certbot 自动续期预期 | 记录真实证书来源与到期日；人工证书建立人工更换提醒 |
| 隧道内正常，公网显示 `Server: Beaver` / `Non-compliance ICP Filing` | 中国大陆云入口的备案接入层在请求到达 Nginx 前拦截 | 保留应用和 Nginx，不做无关修改，交由管理员外部复核备案接入 | 公网验收必须从外部执行并观察响应头；SSH 隧道成功绝不等于公网成功 |
| `systemctl restart` 后紧跟的 `curl` 偶发失败 | 服务还在启动或重启，健康端口尚未 ready | 查看 service 状态并稍后重试健康检查 | 使用有限次数、带间隔的 readiness 检查；持续失败立即查 journal，不无限重试 |
| Windows 本机没有 `openssl` | Windows 环境未安装该工具，不代表证书有问题 | 在 Ubuntu 服务器上用 OpenSSL 完成 SAN、chain 和 key match 核验 | 把证书核验放在证书安装主机执行；不要为了单次核验临时改 Windows 全局环境 |
| 扫描任意不存在路径返回 200 | SPA 的 `try_files $uri $uri/ /index.html` 把未知前端路由回退到 `index.html` | 识别为 SPA fallback，不将 200 误判为敏感文件已泄露 | 对 `/.env`、`/.git`、备份扩展名和隐藏文件增加精确/正则拒绝规则；用响应体、Content-Type 和真实文件存在性判断泄露，而非只看状态码 |

### 6.1 SPA fallback 的建议硬化

上线模板目前为 SPA 提供通用 fallback。后续可在充分测试后，于 `location /` 之前增加对敏感路径和文件类型的拒绝规则，例如拒绝点文件（保留必要的 ACME 例外时单独处理）、`.env`、`.git`、`.sqlite`、`.db`、`.bak`、`.sql`、压缩备份等。修改后必须验证正常前端路由仍回退到 `index.html`，而敏感探测明确返回 404 或 444。

## 7. SSH 图形界面 HTTPS 隧道

### 7.1 建立隧道

在本地 PowerShell 单独打开一个窗口，执行：

```powershell
ssh -N -L 8443:127.0.0.1:443 -i "<SSH_KEY_PATH>" "<SSH_USER>@101.200.137.83"
```

`-N` 表示不启动远端 shell，`-L` 表示把本机 `127.0.0.1:8443` 转发到服务器看到的 `127.0.0.1:443`。命令保持前台无输出通常是正常现象。

### 7.2 用独立 Edge 配置映射正式域名

另开一个本地 PowerShell 窗口：

```powershell
msedge.exe --user-data-dir="$env:TEMP\edge-jerrylab-tunnel" --host-resolver-rules="MAP jerrylab.xyz 127.0.0.1, EXCLUDE localhost" "https://jerrylab.xyz:8443/"
```

浏览器仍以 `jerrylab.xyz` 作为 TLS 主机名，但 TCP 实际连接本机 8443，因此证书域名可以正常校验。独立 `user-data-dir` 避免与已运行的普通 Edge 进程复用配置，导致 host resolver 参数不生效。

### 7.3 验收与关闭

在该浏览器窗口内完成登录、页面路由、API、视频上传和退出登录。生产应用用户名使用 `<PRODUCTION_USERNAME>` 对应的实际值，但不得记录在本文。

关闭方式：在运行 SSH 命令的 PowerShell 窗口按 `Ctrl+C`，再关闭该专用 Edge 窗口。必要时确认本机 8443 已不再监听。

这是本地浏览器 GUI 经 SSH 访问服务器回环 HTTPS 的临时通道，不是公网发布，不证明 DNS、备案接入层或公网安全组正常。

```bash
sqlite3 "/data/mouse-annotation/data/annotation.db" 'SELECT version_num FROM alembic_version;'
```

仅查看当前 revision 时直接只读查询 SQLite，不加载生产 env。需要比较仓库 migration head 时，使用第 6 步相同的 `python-dotenv` + `os.environ.update` + `runpy.run_path` 安全 wrapper 并传入 `--check`；禁止日常运维 `source backend.env`。不要输出用户、凭据或业务敏感表内容。当前已确认 revision 为 `0011`，后续版本应以目标提交 migration head 为准。

### 8.7 SQLite 一致性备份

```bash
umask 0027
timestamp="$(date -u +%Y%m%dT%H%M%SZ)"
sqlite3 "/data/mouse-annotation/data/annotation.db" ".timeout 10000" ".backup '/data/mouse-annotation/backups/annotation-${timestamp}.db'"
sqlite3 "/data/mouse-annotation/backups/annotation-${timestamp}.db" 'PRAGMA integrity_check;'
chmod 0640 "/data/mouse-annotation/backups/annotation-${timestamp}.db"
```

看到 `ok` 只证明该备份文件通过完整性检查，不证明定时任务、媒体备份或恢复流程有效。应定期在隔离路径执行恢复演练，并记录恢复耗时与结果。

## 9. 发布 SOP

1. 选定完整 40 位 `<COMMIT>`，确认它来自预期分支且包含所有部署热修。
2. 创建新的 `/opt/mouse-annotation/releases/<COMMIT>/`，禁止复用或覆盖旧 release。
3. 在新 release 内创建 `.venv`、安装锁定依赖并运行 `pip check`。
4. 显式加载 NVM，执行 `npm ci`、`npm run build`，确认 `frontend/dist/index.html`。
5. 使用稳定 `backend.env`，以 `umask 0027` 先执行迁移检查和迁移。
6. 在切换前完成后端测试证据、真实 FFmpeg 25/30/60 FPS 验收和候选版本检查。
7. 用 `current.next` + `mv -Tf` 原子切换软链接，核对 `readlink` 与 Git hash。
8. 若 unit 有变更，安装 unit 并 `daemon-reload`；restart 后端。
9. 若 Nginx 配置有变更，安装配置，先 `nginx -t`，通过后 reload。
10. 依次验证后端直连、本机 Nginx、SSH 浏览器隧道和公网入口。
11. 保留上一已验证 release，记录数据库 schema 与回滚兼容性。

发布原则是 build/migrate before current，restart/reload after current，health after restart/reload。不要把构建工作放到 `current` 指向的在线目录中进行。

## 10. 回滚 SOP

1. 确定上一已验证 release 的完整提交和数据库兼容性。
2. 查看目标旧 release 的迁移代码是否能读取当前数据库 schema。
3. 如兼容，创建 `current.rollback` 指向旧 release，再用 `mv -Tf` 原子替换 `current`。
4. restart `mouse-annotation.service`；若 Nginx 配置也需回滚，安装对应版本后先 `nginx -t` 再 reload。
5. 验证 systemd、后端健康、本机 HTTPS、登录和关键读写流程。
6. 保留失败 release 和日志用于复盘，不在现场修改不可变 release。

示例模板：

```bash
ln -s "/opt/mouse-annotation/releases/<PREVIOUS_COMMIT>" "/opt/mouse-annotation/current.rollback"
mv -Tf "/opt/mouse-annotation/current.rollback" "/opt/mouse-annotation/current"
sudo systemctl restart mouse-annotation.service
curl --fail --silent --show-error "http://127.0.0.1:8000/api/health"
```

最重要的回滚限制是数据库 schema。代码回滚不等于数据库回滚；若新版本迁移不可逆或旧代码不兼容新 schema，仅切换软链接可能导致数据损坏或服务失败。此时必须基于已验证的一致性备份、迁移设计和停机窗口制定专项回滚方案。

## 12. 学习要点

### 12.1 分离五类资产

代码发布、运行配置、持久数据、secret、证书必须分离：

| 类型 | 正确位置 | 为什么分离 |
|---|---|---|
| 代码发布 | `releases/<COMMIT>` | 可复现、可回滚、不会被运行时写入污染 |
| 稳定配置 | `backend.env` | 发布时不复制 secret，release 切换不改变生产身份 |
| 持久数据 | `/data/mouse-annotation/data` | 不随代码删除或回滚；容量与权限独立管理 |
| secret | 权限 `0600` 的 env、权限 `0600` 的私钥 | 不进入 Git、构建日志、shell 历史和宽权限临时目录 |
| 证书链 | `/etc/nginx/ssl/*.pem` | 由 Nginx 使用并可公开读取，和私钥权限区别管理 |

### 12.2 固定提交，而不是“部署某个分支最新版本”

分支会移动，完整提交哈希不会。release 名称、Git HEAD、`current`、部署配置和验收记录都应能关联到同一固定提交。线上热修如果只改 `/etc`，短期解决了故障，长期却破坏可追溯性，所以必须补成新提交和完整 release。

### 12.3 权限不是部署后的附加项

`chmod` 只能修已有文件，`umask` 决定未来文件。SQLite 会产生 `-wal` 和 `-shm`，上传、日志和导出也会持续产生文件，因此迁移 shell 使用 `umask 0027`、systemd 使用 `UMask=0027`，两者缺一不可。

### 12.4 先验证，再切换

正确顺序是：固定代码 → 安装依赖 → build → 配置校验 → migrate → 真实媒体验收 → 原子切换 → restart/reload → 分层健康检查。把构建或迁移放到切换后，失败就会直接扩大成线上故障。

### 12.5 区分三类问题

| 层次 | 最小验证 | 常见问题 |
|---|---|---|
| 应用层 | `curl 127.0.0.1:8000/api/health` | env、迁移、Python 依赖、端口、FFmpeg、权限 |
| 代理层 | `curl --resolve 域名:443:127.0.0.1 https://域名/...` | Nginx location、TLS、`auth_request`、body size、upstream |
| 云入口层 | 外部网络直接 `curl https://域名/...` | DNS、安全组、备案接入、云 WAF/CDN/拦截页 |

应用直连失败时先查应用；应用直连成功但本机 HTTPS 失败时查 Nginx；本机 HTTPS 和 SSH 隧道都成功但公网失败时查云入口。不要跨层猜测。

### 12.6 如何读日志

1. 先记录故障请求的时间、URL、状态码、文件大小和是否已登录，不记录凭据。
2. 同时间窗看 Nginx 日志，确认请求是否到站、命中了哪个 location、主请求与 `/_auth` 各是什么状态。
3. 若 Nginx 到达 upstream，再看 `mouse-annotation.service` journal 的最早异常和 traceback。
4. 若公网响应服务器头不是 Nginx，优先判断请求未到站，不要继续改 FastAPI。
5. 修改后只复测最小失败路径，再执行完整回归；不要一次改多层配置导致无法归因。
